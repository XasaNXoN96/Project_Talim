# Nginx и определение IP клиента (B-1)

**Статус B-1: механизм проверен на настоящем Nginx 1.24 + gunicorn + clamd в тестовой среде; на боевом сервере НЕ проверен — пункт остаётся блокирующим до проверки там.**

## Что проверялось и чем
`backend/deploy/nginx/verify/run.sh` поднимает **настоящий nginx** (ставится из пакетов ОС) перед **настоящим gunicorn** с отдельной БД, с настоящим `clamd`, и выполняет `checks.py`. Конфигурация — тот же файл, что для production: `backend/deploy/nginx/talim.conf.template` (подставляются только порты/пути).
Разные «клиенты» — адреса `127.0.0.2`, `127.0.0.3`… (петлевой интерфейс Linux). Это **не** настоящая сеть, не TLS и не внешние клиенты.

Результат запуска (все проверки прошли):
| Проверка | Итог |
|---|---|
| Через nginx адрес в журнале входов = реальный адрес клиента, даже если клиент прислал поддельные `X-Forwarded-For`, `X-Real-IP`, `Forwarded` | PASS (3 случая) |
| Прямое обращение к gunicorn с **недоверенного** адреса с поддельным `X-Forwarded-For` — заголовок игнорируется | PASS |
| Ограничитель входа считает по реальному адресу: 20 неудач с `.2` блокируют `.2` (даже с верным паролем) и **не** блокируют `.3`, хотя `.2` подсовывал `X-Forwarded-For: .3` | PASS |
| Два пользователя за одним адресом считаются вместе (политика «общий адрес офиса») | PASS |
| Загрузка файла **ровно 10 МБ** через nginx → gunicorn → настоящий clamd → приватное хранилище | PASS (302, документ создан) |
| 10 МБ + 1 байт: проходит nginx, отклонён приложением | PASS |
| 12 МБ: nginx отвечает 413 со статической страницей, документ не создан | PASS |
| `/private_media/`, `/media/` отвечают 404 на уровне nginx; версия nginx не раскрывается | PASS |
| Приложение «зависло» (SIGSTOP): nginx отвечает 504 через `proxy_read_timeout`, статическая страница; после возобновления работает | PASS |
| Приложение остановлено: 502 со статической страницей, без деталей upstream | PASS |
| **Контроль отрицательный 1:** `DJANGO_TRUSTED_PROXIES` пусто → все клиенты выглядят как `127.0.0.1`, один злоумышленник блокирует вход **всем** | дефект воспроизведён, как ожидалось |
| **Контроль отрицательный 2:** `DJANGO_TRUSTED_PROXIES=127.0.0.0/8` (слишком широко) → поддельный заголовок принимается | дефект воспроизведён, как ожидалось |

Отрицательные контроли доказывают, что проверки чувствительны: они «краснеют» при неверной настройке.

## Как устроено доверие
1. nginx — единственная публичная точка входа. Он **перезаписывает** `X-Forwarded-For` значением `$remote_addr` (не дописывает) и всегда подключается к приложению с `127.0.0.1` (`proxy_bind`).
2. Приложение: `DJANGO_TRUSTED_PROXIES=127.0.0.1` — доверяет заголовкам **только** от этого адреса (`apps/core/network.py`). Любой другой адрес — заголовки игнорируются.
3. gunicorn слушает **только** `127.0.0.1` (или unix-сокет) — иначе клиент обойдёт nginx. (В тесте gunicorn намеренно слушает `0.0.0.0`, чтобы проверить прямое обращение с недоверенного адреса.)
4. Если перед nginx стоит ещё один прокси/балансировщик, его адрес нужно добавить и в конфигурацию nginx (`real_ip`), и в `DJANGO_TRUSTED_PROXIES` — иначе все клиенты снова станут «одним IP». Этот случай **не** проверялся.
5. Никогда не указывайте в `DJANGO_TRUSTED_PROXIES` сети пользователей или `0.0.0.0/0`.

## Как воспроизвести
```bash
sudo apt-get install nginx            # плюс backend/.venv с зависимостями, PostgreSQL с ролью, умеющей создавать БД
backend/deploy/nginx/verify/run.sh    # создаёт и удаляет БД talim_nginx_check; логи остаются в /tmp/talim-nginx-*/logs
```
Для загрузки через настоящий антивирус нужен работающий `clamd` (см. CLAMAV.md); без него скрипт сообщит и прогонит загрузку без антивируса.

## Что нужно проверить на боевом сервере (чек-лист закрытия B-1)
- [ ] Подставить настоящее имя, TLS-сертификат (`listen 443 ssl`, HTTP → HTTPS редирект), пути.
- [ ] Из **внешней сети** (не с сервера): неудачный вход → в журнале аудита реальный публичный адрес; запрос с поддельным `X-Forwarded-For` не меняет его.
- [ ] Порт gunicorn закрыт межсетевым экраном снаружи (`curl http://<публичный-IP>:8000` не отвечает).
- [ ] Сходится ли адрес nginx для приложения с `DJANGO_TRUSTED_PROXIES` (если nginx и приложение на разных машинах — укажите адрес nginx).
- [ ] `client_max_body_size`, тайм-ауты и страницы ошибок действуют на боевой конфигурации; загрузка 10 МБ с реального канала.
- [ ] `check --deploy` на сервере.

## Ограничения
- Не проверено: TLS, HTTP/2, реальная сеть/NAT/балансировщик, IPv6-клиенты через nginx, поведение при большом числе одновременных загрузок.
- `proxy_request_buffering on`: nginx принимает файл целиком до передачи приложению — на медленных каналах дольше удерживает соединение; `client_body_timeout 30s` может оборвать очень медленную загрузку.


## Видео к достижениям: отдельный лимит тела запроса
Общий лимит `client_max_body_size 11m` остаётся. Для двух адресов форм достижений (`/portal/achievements/new/` и `/portal/achievements/<uuid>/edit/`) в обоих шаблонах есть отдельный `location` с `client_max_body_size 22m`, `client_body_timeout 120s` и увеличенными таймаутами (антивирус проверяет видео до 90 с). Регулярное выражение в **кавычках**: фигурные скобки `{36}` без них nginx воспринимает как начало блока и не запускается (обнаружено командой `nginx -t`). Проверено в песочнице: шаблоны проходят `nginx -t`; тело 24 МБ на форму достижения отклоняется (413), 19 МБ доходит до приложения, 12 МБ на любой другой адрес отклоняется. Проверить на боевом сервере: загрузка видео ~15–20 МБ с реального канала через настоящий Nginx.


## Галерея «Media»: лимиты загрузки
Два адреса получили свои `location` в обоих шаблонах: `= /portal/media/new/photos/` (`client_max_body_size 100m`, `client_body_timeout 180s`, таймауты 180 с: до 12 фото по 8 МБ, каждое сканируется отдельно) и `= /portal/media/new/video/` (`22m`, 120 с). Проверено: оба шаблона проходят `nginx -t`; тест `GalleryUploadLimits` следит, чтобы 12 × 8 МБ помещались в лимит фото, а видео — в лимит видео. На боевом сервере проверить загрузку 12 настоящих фото с реального канала.
