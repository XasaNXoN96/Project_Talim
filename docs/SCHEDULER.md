# Планировщик и фоновые задачи (День 12)

**Статус: команды, единый запуск, контроль результата и конфигурация готовы и проверены в тестовой среде; расписание НЕ установлено ни на одном сервере.** Ничего из перечисленного ниже не выполняется само, пока на сервере не включены таймеры. Новая инфраструктура (Celery, Redis, брокер очередей) не нужна и не добавлялась: все задачи короткие, периодические и безопасны при повторе.

## 1. Инвентаризация задач

| Задача (команда) | Назначение | Частота | Окружение | Защита от параллельного запуска | При ошибке | Как проверить результат |
|---|---|---|---|---|---|---|
| `send_task_reminders` | уведомления «срок скоро / просрочено» исполнителям открытых заданий | каждый час | БД; e-mail копии — только если `NOTIFICATION_EMAILS_ENABLED` и SMTP | advisory-блокировка БД + уникальный ключ уведомления | сбой одной записи считается, остальные обрабатываются; код 1 | `job_status`, страница «Fon vazifalari», `due_soon=… overdue=…` |
| `purge_employee_imports` | стереть разобранные строки (ПДн) непотверждённых предпросмотров импорта | каждые 15 мин | БД | advisory-блокировка | код 1 | `job_status`; счётчик `wiped` |
| `clear_expired_sessions` | удалить просроченные сессии Django и устаревшие записи указателя «активных сессий» | раз в сутки | БД | advisory-блокировка | код 1 | `job_status` |
| `purge_throttles` | удалить строки ограничителя попыток, у которых блокировка кончилась и окно прошло | каждый час | БД | advisory-блокировка | код 1 | `job_status` |
| `check_scanner` | проверка антивируса (PING + пробная проверка) | каждые 5 мин | clamd (сокет/порт) | advisory-блокировка | код 1 — загрузки файлов в это время **отклоняются** (fail-closed) | `job_status` / оповещение `OnFailure` |
| `verify_document_files` | целостность хранилища: файл есть, размер и SHA-256 совпадают | раз в неделю (и после восстановления) | БД + чтение `PRIVATE_MEDIA_ROOT` | advisory-блокировка | код 1 при любом расхождении | `job_status` |
| `scan_documents` | повторная проверка версий, загруженных при выключенном сканере (`--all` — после обновления сигнатур) | **по требованию**, не по расписанию | БД + clamd + файлы | advisory-блокировка | сканер недоступен → ничего не меняется, код 1; нечитаемый файл — ошибка записи, код 1 | `job_status` |
| `job_status` | сводка по всем задачам для мониторинга | по необходимости (мониторинг) | БД | — (только чтение) | код 1, если хоть одна задача нездорова | сам вывод |

Не создавались дубликаты: `clear_expired_sessions` — единственная новая команда задачи, и она **заменяет** в расписании штатную `clearsessions` (делает то же и дополнительно чистит указатель сессий и записывает запуск). `seed_roles` и `reset_2fa` — разовые административные команды, в расписание не входят.

## 2. Как работает единый запуск (`apps/core/jobs.py`)
Каждая задача — наследник `TrackedCommand`:
* **Блокировка:** `pg_try_advisory_lock` с отдельным номером на задачу (работает между процессами и серверами). Второй запуск при занятой блокировке **сразу выходит с кодом 0** и пишет «skipped»; он не считается запуском и не затирает настоящий последний результат.
* **Запись запуска** `JobRun`: начало, конец, статус, обработано, ошибок и **только имя класса** исключения. Сообщений исключений, путей, содержимого записей и секретов там нет. Хранится не более 200 последних запусков каждой задачи.
* **Коды выхода:** 0 — всё прошло; 1 — аварийное завершение **или** сбой хотя бы одной записи. Блокировка снимается в любом случае.
* **Журнал** (`apps.jobs`): имя задачи, счётчики, id записей и класс исключения. Заголовки заданий, адреса, тексты исключений и трассировки в журнал не попадают (трассировка — только на уровне DEBUG, то есть не в production).
* **Идемпотентность:** напоминание — по ключу `(пользователь, ключ «вид:задание:срок»)` с уникальным ограничением БД; даты считаются по **местному** времени (`Asia/Tashkent`, UTC+5, без перехода на летнее время), поэтому полночь по Ташкенту не создаёт дубликатов (проверено тестом). Очистки трогают только то, что истекло: живые сессии и их записи, незавершённые и свежие предпросмотры, активные блокировки попыток не удаляются.

## 3. Контроль: `job_status` и страница «Fon vazifalari»
```bash
python manage.py job_status            # таблица; код 1, если что-то нездорово
python manage.py job_status --json     # для мониторинга
python manage.py job_status --job send_task_reminders
```
Состояния берутся **только из записанных запусков**: `success` — последний запуск успешен; `failed` — ошибка (показан класс); `running` — выполняется сейчас; `never` — запусков не записано (**не** «всё хорошо»); `unknown` — запуск начат и не завершён дольше 30 минут (процесс убит или завис). Отдельно «опаздывает» (`OVERDUE`): у периодической задачи нет успеха новее двух интервалов (в том числе если успеха не было ни разу). Здоровой считается задача в состоянии `success`/`running` без опоздания; задачи «по требованию» не опаздывают.

Та же сводка — в портале на `/portal/jobs/` для ролей с правом чтения журнала аудита (администратор, системный администратор). Страница показывает названия, состояния, время, счётчики — **без** путей, настроек, секретов и персональных данных.

## 4. Установка на сервере (systemd — основной вариант, cron — запасной)
Почему systemd: журнал (`journalctl`), `Persistent=true` (пропущенный запуск догоняется после перезагрузки), `OnFailure=`, изоляция процесса. Cron — когда systemd недоступен; 5-минутная проверка антивируса и недельная проверка целостности подходят для обоих.

Файлы (`backend/deploy/`):
* `systemd/talim-job@.service` — **один шаблон на все задачи** (имя экземпляра = команда `manage.py`), от пользователя `talim`, `ProtectSystem=strict`, `NoNewPrivileges`, `UMask=0077`, таймаут 15 мин, `OnFailure=talim-job-failed@%n.service`;
* `systemd/talim-<задача>.timer` — по таймеру на каждую периодическую задачу (расписание и `Persistent` — см. файлы);
* `systemd/talim-job-failed@.service` — пишет в журнал `user.err` (замените `ExecStart` на свою отправку оповещения; секреты не в файле);
* `systemd/crontab.example` — тот же набор для cron (`flock -n`, абсолютные пути, `umask 077`, журнал в `/var/log/talim/`);
* `tmpfiles.d/talim.conf` — каталоги `/run/talim` (lock-файлы) и `/var/log/talim` (`0750 talim:talim`);
* `logrotate/talim` — ротация журналов cron-варианта (`0640 talim:talim`);
* `verify_deploy_files.sh` — проверка файлов без установки.

```bash
# 1) пользователь и права (один раз)
sudo useradd --system --home /srv/talim --shell /usr/sbin/nologin talim
sudo install -d -o root -g talim -m 0750 /etc/talim
sudo install -o root -g talim -m 0640 /dev/null /etc/talim/talim.env    # заполнить значениями из backend/.env.example; в Git не попадает
sudo cp backend/deploy/tmpfiles.d/talim.conf /etc/tmpfiles.d/ && sudo systemd-tmpfiles --create
sudo cp backend/deploy/logrotate/talim /etc/logrotate.d/talim
# 2) systemd (поправьте пути/User при другом размещении)
sudo cp backend/deploy/systemd/talim-job*.service backend/deploy/systemd/talim-*.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start talim-job@send_task_reminders.service && journalctl -u talim-job@send_task_reminders.service -n 20   # ручной пробный запуск
sudo systemctl enable --now talim-send_task_reminders.timer talim-purge_employee_imports.timer talim-purge_throttles.timer \
     talim-clear_expired_sessions.timer talim-check_scanner.timer talim-verify_document_files.timer
systemctl list-timers 'talim-*'
# 3) контроль
sudo systemctl start talim-job@job_status.service; echo $?     # 0 = все задачи здоровы
```
**Права:** `talim.env` — владелец `root`, группа `talim`, режим `0640` (читает только служба; не в репозитории, не в журнале); `/var/log/talim` — `0750 talim:talim`, файлы журналов `0640`; пользователь `talim` не `root`, не в группе `sudo`, без оболочки входа. Переменные окружения не печатаются ни одной задачей. Cron-вариант: `sudo crontab -u talim backend/deploy/systemd/crontab.example` (никогда от `root`). Старые `talim-reminders.service/.timer` заменены этим набором: если они были установлены, отключите их (`systemctl disable --now talim-reminders.timer`).

## 5. Что проверено и как
* **Тесты** (`apps/core/tests_jobs.py`, `tests_deploy_files.py`, `apps/notifications/tests.py`): повторный запуск; параллельный запуск (потоки БД, `TransactionTestCase`, для каждой задачи); просроченные записи; сбой одной записи при продолжении остальных; идемпотентность напоминаний вокруг местной полуночи; коды выхода через настоящий путь командной строки (`run_from_argv`); отсутствие секретов, заголовков и адресов в журналах и сообщениях; защита живых данных от очистки; состояния `never/running/unknown/success/failed` и «опаздывает»; страница и права; согласованность файлов развёртывания (у каждой задачи есть таймер и cron-строка, `User=talim`, абсолютные пути, нет значений секретов).
* **Проверка файлов** `backend/deploy/verify_deploy_files.sh`: `systemd-analyze verify` во временном корне (выявляет неизвестные директивы и неверный `OnCalendar` — проверено намеренной порчей), выражения `OnCalendar`, синтаксис crontab, разбор конфигурации logrotate.
* **Реальный запуск** тем же способом, что и юнит/cron-строка: `env -i`, файл окружения, `flock`, абсолютные пути, на тестовой БД с вымышленными данными: все команды выполнены, коды 0/1 соответствуют; два одновременных реальных процесса — один пропущен; `check_scanner` и `scan_documents` — с настоящим clamd (ClamAV 1.5.4, **локальная** сигнатура EICAR, не официальная база).

## 6. Не проверено (нужен реальный сервер)
* Фактическая работа systemd-таймеров и cron: **в среде нет systemd как PID 1** — файлы проверены статически и командами; запуск по расписанию, `Persistent` после перезагрузки, `OnFailure` и права пользователя `talim` на реальных каталогах не проверялись.
* Оповещение при сбое: юнит лишь пишет в журнал; доставка письма/сообщения дежурному не настроена.
* Официальная база ClamAV, нагрузка `verify_document_files` на большом хранилище, SMTP при `NOTIFICATION_EMAILS_ENABLED`, несколько серверов приложения (блокировка работает через общую БД, но не проверялась на нескольких узлах).
* Резервное копирование не отслеживается `job_status` и по-прежнему без расписания (см. BACKUP_AND_RESTORE.md).
