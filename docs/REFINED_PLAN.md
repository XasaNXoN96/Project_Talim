## 1. Рекомендуемый минимальный стек

| Слой | Рекомендация | Что отложено |
|---|---|---|
| Приложение | **Один серверный монолит** с серверным рендерингом страниц | Отдельный API-сервис |
| База данных | **PostgreSQL** | — (нужна с первого дня) |
| Файлы | Диск сервера под управлением приложения, с копированием наружу | S3-совместимое хранилище |
| Веб-сервер | Nginx + бесплатный TLS | CDN |
| Сессии, фоновые задачи | В PostgreSQL и системный планировщик | Redis |
| Уведомления | Обновление по таймеру (раз в 30–60 с) и письма | WebSocket |
| Чат | Не входит в вариант B | WebSocket + Redis |

### 1.1 Нужен ли отдельный NestJS, Redis и WebSocket с первого дня

| Компонент | Нужен сразу? | Почему и когда добавить |
|---|---|---|
| **Отдельный API (NestJS)** | **Нет** | Он нужен, если появятся мобильное приложение, сторонние клиенты или отдельная команда фронтенда. Для сайта и портала достаточно монолита. Модули внутри монолита делаем раздельными, чтобы при необходимости вынести API без переписывания |
| **Redis** | **Нет** | Сессии хранит PostgreSQL. Фоновые задачи на старте — по расписанию. Redis появляется, когда нужны чат, очереди с большим потоком писем/SMS или кэш под нагрузкой |
| **WebSocket** | **Нет** | Нужен для чата. Уведомления и задания спокойно работают на обновлении по таймеру. Добавляется вместе с чатом |
| **Очередь задач** | Нет | Обработка изображений и антивирус — сразу при загрузке или по расписанию. Очередь — когда загрузок станет много |
| **Отдельный поиск** | Нет | Хватит полнотекстового поиска PostgreSQL |

### 1.2 Сравнение вариантов стека

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **A. Монолит с серверными шаблонами** (например, Django + PostgreSQL) | Всё в одном; готовая админка, пользователи, права, миграции; **текущий HTML/CSS переиспользуется почти напрямую**; меньше всего частей для эксплуатации | Интерактивность через небольшой JS; сложные «живые» экраны (чат) — позже | **Рекомендую**, если нет сильной JS-команды |
| **B. Монолит на Node** (Next.js как fullstack + PostgreSQL, без отдельного API) | Один язык; хорошо, если команда на JS | Нужно переписать страницы в React; больше своего кода на права и админку | Хороший выбор, если команда на JS |
| **C. Next.js + NestJS + PostgreSQL + Redis** (прежний документ) | Гибко, готово к росту и мобильному приложению | Больше частей, выше стоимость и срок; избыточно на старте | Не нужно на старте |
| **D. Готовый облачный бэкенд-сервис** (BaaS) | Быстрый старт | Данные за рубежом — **риск по локализации [проверить]**; зависимость от поставщика | Не рекомендую для персональных данных |
| **E. Готовая CMS (WordPress и др.) + доработки** | Быстро запустить публичный сайт | Портал и права придётся строить отдельно; двойная работа; риски безопасности плагинов | Только если публичный сайт нужен очень срочно |

**Рекомендация:** вариант A (или B, если команда на JS) с PostgreSQL. Выбор между A и B — ответ на вопрос 1 заказчику; на сроки и расходы он влияет мало, на найм и поддержку — сильно.

## 2. Использовать текущий HTML/CSS/JS и переносить постепенно

Это возможно и **рекомендуется**.

### 2.1 Что переиспользуется

| Часть | Как |
|---|---|
| `styles.css` | Без изменений: токены и все компоненты |
| HTML-страницы | Становятся шаблонами: общий каркас (шапка, подвал, сайдбар, топбар) — в базовых шаблонах, содержимое страницы — отдельно |
| Иконки | Из JS в серверную подстановку (inline SVG), чтобы работали без JS |
| Поведение (сайдбар, модальные окна, вкладки, лайтбокс, выпадающие меню) | Остаётся в `app.js` как улучшение страниц |
| Сетки, адаптивность, пустые состояния | Без изменений |

### 2.2 Что уходит
`data.js` (данные из БД), сборка шапки/подвала/сайдбара в JS (в шаблоны — заодно появляется нормальный SEO и работа без JS), фильтры из `pages.js` (запросы к базе), имитация входа, «Maket»-кнопки (реальные действия), Google Fonts (свой хостинг).

### 2.3 Порядок переноса (по одной странице)
1. Базовые шаблоны (публичный и портальный) + выгрузка CSS/JS как статических файлов.
2. Публичные страницы: главная → новости → педагоги → медиа → организация → документы.
3. Вход и каркас портала.
4. Страницы портала по мере появления функций (этапы 3–7).
5. После каждой страницы — сверка внешнего вида с эталоном (`design-v1`) на тех же ширинах.

Эталон: тег `design-v1` на текущем HEAD; демо на GitHub Pages остаётся нетронутым.

### 2.4 Экономия
Не переписываем 24 страницы в другой фреймворк и не строим отдельный API. По оценке, это экономит порядка 10–15 % общих трудозатрат варианта B (≈ 70 → ≈ 60–65 человеко-недель). Оценка не подтверждена опытом на этом проекте и уточняется после этапа 0.

## 5. Что можно делать с помощью Claude, а что проверяет специалист

Принцип: **Claude готовит, человек проверяет и принимает.** Claude не получает доступа к боевым серверам и паролям; работа идёт в репозитории и на staging; запуск на production выполняет и подтверждает человек.

### Можно поэтапно делегировать Claude (с обычной проверкой кода и просмотром результата)
- Перенос страниц из текущего HTML в шаблоны, сверка с эталоном на 360–1440 px.
- Модели данных, миграции, CRUD-разделы, формы, фильтры, пагинация.
- Админ-разделы для редакторов, публичные страницы, SEO-разметка.
- Автоматические тесты, настройка проверок кода (CI), документация, инструкции пользователям.
- Подготовка заготовок политик и согласий (**черновик, не юридический текст**).
- Исправление доступности, адаптивности, производительности.
- Подготовка данных для импорта из таблиц.

### Требует проверки специалистом
| Область | Что именно проверяет человек |
|---|---|
| **Безопасность входа** | Схема сессий, пароли, вторая проверка, восстановление, ограничение попыток — независимый просмотр кода |
| **Права доступа** | Продуманность матрицы ролей и тестов; ручная проверка подмены адресов |
| **Загрузка файлов** | Антивирус, ограничения типов и размеров, безопасная выдача файлов |
| **Защита от XSS и других атак** | Очистка HTML редактора, политика безопасности содержимого, заголовки |
| **Персональные данные** | Юрист: локализация данных, регистрация баз, сроки хранения, форма согласий (в том числе родителей на фото детей) **[проверить]** |
| **Геолокация сотрудников** | Юрист: допустимость и условия **[проверить]**; решение заказчика |
| **Инфраструктура** | Настройка сервера, межсетевого экрана, обновлений, резервных копий и **проверка восстановления** — опытный DevOps |
| **Тест на проникновение** | Независимая команда перед запуском портала |
| **Перенос реальных персональных данных** | Ответственный сотрудник заказчика + проверка доступов |
| **Запуск на production и реагирование на инциденты** | Человек с доступом и ответственностью |
| **Соответствие требованиям к государственным ресурсам** | Специалист по требованиям **[проверить]** |

## 8. Критерии перехода к следующему этапу

Переход к следующему этапу — только при выполнении **всех** пунктов текущего:

1. Критерии готовности этапа (раздел 3) выполнены и показаны заказчику на staging.
2. Автоматические проверки зелёные; критических и высоких замечаний по безопасности нет.
3. Резервное копирование работает, восстановление проверено (с этапа 1).
4. Заказчик письменно принял этап.
5. Для этапов 2, 3, 5 дополнительно: проверка специалистом по безопасности и подтверждение юриста по персональным данным.
6. Обновлены оценка сроков и бюджета следующего этапа.
