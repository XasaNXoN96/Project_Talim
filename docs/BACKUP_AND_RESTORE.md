# Резервное копирование и восстановление

**Статус: скрипты написаны; восстановление выполнено на тестовых данных на той же машине в отдельную БД и каталог (см. ниже). Восстановление на чистой машине, с боевыми данными и ключами — НЕ выполнялось: пункт B-7 остаётся открытым.**

## Что копируется и как обеспечивается согласованность
| Что | Как |
|---|---|
| PostgreSQL | `pg_dump --format=custom` — согласованный снимок (одна транзакция) |
| Приватное хранилище файлов (`PRIVATE_MEDIA_ROOT`: версии документов и вложения заданий) | архив `tar` |
| **Порядок** | **сначала БД, потом файлы.** Файлы приложением не перезаписываются и не удаляются (случайные имена; «удаление вложения» лишь отвязывает), поэтому каждый файл, на который ссылается дамп, есть в архиве; файлы, загруженные между шагами, — лишние, но безвредные. Если это поведение изменится — останавливайте приложение на время копии |

**Не копируются и не должны попадать в копии:** `.env`, ключи (`SECRET_KEY`, `OTP_ENCRYPTION_KEYS`), пароли БД/почты, сертификаты. Скрипт читает только БД и каталог файлов (и дополнительно исключает `.env*`, `*.key`, `*.pem`). Секреты хранятся отдельно (менеджер паролей/хранилище секретов).
⚠️ **Без `OTP_ENCRYPTION_KEYS` восстановленная БД бесполезна для 2FA** (секреты TOTP зашифрованы этим ключом): ключ нужно хранить отдельно от копий и тоже иметь его резервную копию (но не рядом с дампом).

## Защита копий
- Оба файла шифруются (AES-256-CBC, PBKDF2 600 000 итераций, соль) **до** того, как остаются на диске; незашифрованные временные файлы удаляются (`shred`).
- Каталог копий — права `700`, файлы `600`; пароль шифрования — в файле `600`, **вне репозитория и вне каталога копий**; его копия — в другом месте (потеря пароля = потеря копий).
- Хранить копии на **другой машине/диске**, чем сервер (иначе пожар/диск = потеря всего); желательно с ограничением доступа и неизменяемым хранением. Копии содержат персональные данные: к ним применяются те же юридические требования, что и к рабочей БД (срок хранения, размещение — см. LEGAL_AND_DATA_CHECKLIST.md).
- Целостность зашифрованных файлов проверяет `MANIFEST.sha256` (до расшифровки).

## Создание копии
```bash
export BACKUP_DIR=/var/backups/talim BACKUP_PASSPHRASE_FILE=/etc/talim/backup.pass   # chmod 600
export PRIVATE_MEDIA_ROOT=/var/lib/talim/private_media
export PGHOST=... PGPORT=5432 PGUSER=talim_backup PGDATABASE=talim PGPASSFILE=/etc/talim/.pgpass
backend/deploy/backup/backup.sh        # BACKUP_KEEP=14 — сколько последних копий хранить
```
Запускайте по расписанию (systemd timer/cron раз в сутки) и **копируйте результат вне сервера**. Планировщик для копий на сервере не настроен.

## Проверка восстановления (в отдельную БД и каталог)
```bash
export BACKUP_PASSPHRASE_FILE=... BACKEND_DIR=/srv/talim/backend PYTHON=/srv/talim/backend/.venv/bin/python
export PGHOST=... PGUSER=...   # пользователь, умеющий создавать БД
backend/deploy/backup/restore_check.sh /var/backups/talim/talim-20261017T022238Z
```
Скрипт: (1) проверяет контрольные суммы, (2) расшифровывает, (3) восстанавливает БД в **временную** базу `talim_restore_check`, (4) распаковывает файлы в **временный** каталог, (5) `manage.py migrate --check` и `manage.py verify_document_files` (каждая версия/вложение: файл есть, размер и SHA-256 совпадают), (6) печатает число записей. Скрипт **отказывается** работать, если имя БД совпадает с рабочей или не содержит `restore`/`scratch`/`check`. Временные БД и файлы удаляются (`KEEP=1` — оставить).

Для реального восстановления после аварии: те же шаги 1–4 в боевую БД (остановив приложение), затем `migrate`, `seed_roles`, `verify_document_files`, `check_scanner`.
