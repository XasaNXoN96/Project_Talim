# Резервное копирование и восстановление (обновлено в День 13)

**Статус: скрипты, их запуск как контролируемых задач и расписание подготовлены; создание копии и восстановление в изолированную среду проверены на тестовых данных на этой же машине. Расписание НЕ установлено, копии НЕ вынесены за пределы сервера, восстановление на чистой машине с боевыми данными и ключами НЕ выполнялось — пункт B-7 остаётся открытым.**

## 1. Что входит в копию и что нет
| Входит | Как |
|---|---|
| PostgreSQL | `pg_dump --format=custom` — один согласованный снимок |
| Приватное хранилище (`PRIVATE_MEDIA_ROOT`: версии документов, вложения заданий) | `tar`; из архива исключены `.env*`, `*.key`, `*.pem`, `*.tmp`, `*.part`, `*.lock`, `*.log` |
| **Порядок** | **БД первой, файлы потом**: файлы приложением не перезаписываются и не удаляются (случайные имена), поэтому каждый файл, на который ссылается дамп, есть в архиве; загруженные между шагами — лишние, но безвредные. Если поведение изменится — останавливать приложение на время копии |

**Намеренно НЕ входит (хранить отдельно, тоже защищённо и тоже с резервной копией):**
* `/etc/talim/talim.env`: `DJANGO_SECRET_KEY`, пароль БД, SMTP; **`OTP_ENCRYPTION_KEYS`** — без него восстановленная БД бесполезна для 2FA (секреты TOTP зашифрованы им): администраторам пришлось бы заново настраивать 2FA;
* пароль шифрования копий (файл `BACKUP_PASSPHRASE_FILE`) — ключ **не лежит внутри архива, который он открывает**, и скрипт отказывается работать, если файл ключа находится в каталоге копий или в хранилище документов;
* сертификаты TLS, конфигурация Nginx (шаблон — в репозитории), конфигурация ClamAV.
Потеря пароля шифрования = потеря всех копий; хранить его копию отдельно от копий данных.

## 2. Аудит прежней версии и что исправлено
| Было | Стало |
|---|---|
| дамп и `tar` сначала писались на диск **в открытом виде**, затем шифровались | потоковое шифрование: `pg_dump \| openssl`, `tar \| openssl` — открытых данных на диске нет; сбой любой стороны конвейера (`pipefail`) = сбой всего запуска |
| копия писалась сразу в итоговый каталог; неудачный запуск оставлял неполный каталог, который **учитывался в хранении** и мог вытеснить хорошие копии | запись в `talim-<штамп>.partial`, переименование в итоговое имя только после полного успеха; при сбое каталог удаляется; хранение считает только полные копии и вообще не выполняется при сбое |
| защиты от одновременного запуска в самом скрипте не было | `flock` на `.backup.lock` в каталоге копий: второй запуск ничего не делает и выходит с кодом 75 |
| успех = «файлы записаны» | дополнительно: манифест перепроверяется, дамп читается `pg_restore --list`, архив — `tar --list`; в `INFO.txt` записано `readable_check=ok` и **`restore_verified=no`** |
| проверка ключа: только права `600` | также: не короче 20 символов, не в каталоге копий и не в хранилище; каталог копий — `700` |
| восстановление расшифровывало данные во временные файлы | поток прямо в `pg_restore`/`tar`; временных открытых файлов нет |
| проверка восстановления: целостность файлов и счётчики | дополнительно: `migrate` на копии (старые копии получают новые миграции — это нормально и отражается в отчёте), число «осиротевших» файлов, и **настоящая проверка доступа**: реальный обработчик скачивания на восстановленной копии, с существующими правами (аноним отклонён, разрешённый пользователь получает файл с тем же SHA-256, не разрешённый — 403) |
| код 1 при любом сбое | коды: 0 — успех, 1 — сбой шага, 2 — неверная конфигурация (ничего не начато), 75 — занято (не сбой) |

Журнал скриптов: имена и счётчики; пароль шифрования, пароль БД, ключи и содержимое данных в вывод не попадают (проверено тестами).

## 3. Контроль через общий механизм задач
Две Django-команды запускают скрипты и записывают результат в `JobRun` (`apps/core/backup_jobs.py`):

| Задача (`job_status`, страница «Fon vazifalari») | Команда | Что означает «успешно» | Чего НЕ означает |
|---|---|---|---|
| `backup_create` — «Zaxira nusxa yaratildi» | `manage.py run_backup` (раз в сутки) | архив записан, манифест верен, дамп и архив читаются | что копия восстанавливается; что она лежит вне сервера |
| `backup_restore_check` — «Zaxira nusxadan tiklash tekshirildi» | `manage.py run_restore_check` (раз в неделю) | **самая новая полная копия** восстановлена в отдельную БД и каталог и прошла все проверки (раздел 5) | что восстановление пройдёт на чистой машине с боевыми ключами; что копия вне сервера |

Это **два разных факта**, они не подменяют друг друга: сколько бы архивов ни лежало, статус «восстановление проверено» остаётся «ещё не запускалась», пока проверка не выполнялась. «Давно не создавалась» → «опаздывает» (последний успех старше двух интервалов), «ещё не запускалась», «результат неизвестен» (запуск начат и не завершён) — как у остальных задач. Одновременный запуск: блокировка БД + `flock` скрипта; занятый запуск — пропуск без записи. В записи запуска: число файлов, имя каталога копии (метка времени), класс ошибки — никаких путей, паролей и сообщений. Скрипты можно запускать и без Django (cron напрямую) — тогда результат в `job_status` не попадёт.

Страница задач всегда напоминает: **копия на этом же сервере не защищает от потери сервера**; вынос копии наружу этими задачами не проверяется.

## 4. Создание копии
Окружение (файл `/etc/talim/backup.env`, `root:talim 0640`, только имена и пути; пароли — в отдельных файлах `0600`):
```
BACKUP_DIR=/var/backups/talim                      # каталог 0700, владелец — пользователь службы
BACKUP_PASSPHRASE_FILE=/etc/talim/backup.pass      # 0600, ≥ 20 символов, вне BACKUP_DIR и вне хранилища документов
PGPASSFILE=/etc/talim/backup.pgpass                # 0600; роль с правом чтения БД (лучше отдельная, не рабочая роль приложения)
# при необходимости: PGHOST PGPORT PGUSER PGDATABASE PRIVATE_MEDIA_ROOT BACKUP_KEEP=14
```
```bash
python manage.py run_backup            # как задача (рекомендуется: запись в job_status)
backend/deploy/backup/backup.sh        # напрямую
```
**Хранение:** `BACKUP_KEEP` (по умолчанию 14) последних **полных** копий; ротация выполняется только после успешной новой копии. Расписание, пользователь, пути и права — [SCHEDULER.md](SCHEDULER.md) §4.

## 5. Проверка восстановления (в отдельную БД и каталог)
```bash
python manage.py run_restore_check     # самая новая полная копия, с записью в job_status
backend/deploy/backup/restore_check.sh /var/backups/talim/talim-<штамп>   # напрямую
```
Шаги: (1) манифест; (2) временная БД `talim_restore_check`; (3) `pg_restore` (расшифровка «на лету»); (4) файлы во временный каталог; (5) `migrate` на копии, затем каждая версия/вложение: файл есть, размер и SHA-256 совпадают (+ счёт лишних файлов), затем **реальные ответы обработчика скачивания** по выборке документов каждого уровня доступа; (6) счётчики записей. По завершении (успех или сбой) временные БД и каталог удаляются (`KEEP=1` — оставить). Скрипт **отказывается** работать, если имя БД совпадает с рабочей (`PGDATABASE`/`DB_NAME`), не содержит `restore`/`scratch`/`check`, или каталог файлов не пуст. Команда проверки доступа дополнительно отказывается запускаться без `RESTORE_CHECK=1` и «чужого» имени БД. Неверный пароль, повреждённый архив, повреждение за переписанным манифестом — отказ, код ≠ 0, временные данные удалены.

Реальное восстановление после аварии: остановить приложение → шаги (3)–(4) в чистую БД и каталог → `migrate` → `seed_roles` не нужен (роли в БД) → `verify_document_files`, `check_scanner` → вернуть `talim.env` с **тем же** `OTP_ENCRYPTION_KEYS` → запустить приложение.

## 6. Копия вне сервера
Копия в `BACKUP_DIR` на том же диске/сервере защищает только от ошибки в данных, но не от потери диска, сервера или помещения. Нужно второе место: **другая машина** (например, `rsync`/`borg`/`restic` по SSH на отдельный сервер, ключ только на запись/добавление) или **объектное хранилище** с неизменяемостью (object lock) и отдельными учётными данными, не доступными приложению. Копии уже зашифрованы, поэтому выносить можно как есть; пароль шифрования туда не выносить. Этот этап **не реализован и не проверен**: нужна инфраструктура заказчика и юридическое решение о размещении (копии содержат персональные данные — [LEGAL_AND_DATA_CHECKLIST.md](LEGAL_AND_DATA_CHECKLIST.md)). Контроль «копия действительно доехала» должен быть отдельной задачей на стороне получателя.

## 7. Что реально проверено (День 13)
* **Автотесты** (`apps/core/tests_backup.py`, 25 тестов, настоящие `pg_dump`, `openssl`, `tar`, `pg_restore`, тестовая PostgreSQL, одноразовый пароль, вымышленные данные): зашифрованность и права файлов; отсутствие открытых временных файлов; исключение подложенных `.env`/`.key`/`.pem`/`.log`; отсутствие паролей и ключей в архиве и выводе; повтор и ротация; сбой не стоит ни одной существующей копии и не оставляет `.partial`; сбой архиватора посреди запуска; отказ при неверной конфигурации; одновременный запуск (75); восстановление проходит все проверки, **доступ через реальный обработчик** (аноним отклонён, разрешённый получает идентичные байты, неразрешённый — 403), живая БД не тронута, временные БД и каталоги удалены; отказ при неверном пароле, повреждённом архиве, урезанном дампе за переписанным манифестом и **изменённом байте внутри документа** (ловится SHA-256); отказ при небезопасных целях; запись в `job_status` как двух разных фактов; сбой/пропуск/зависание скрипта; отсутствие секретов в записях и логах; «давняя копия» = опаздывает.
* **Мутационные проверки:** семь намеренных поломок (нет `pipefail`, нет проверки места пароля, нет защиты имени БД, нет проверки манифеста, не сравнивается SHA-256, обёртка игнорирует код выхода, пропуск проверки доступа) — каждая роняет тесты.
* **Ручной прогон на dev-БД с вымышленными данными** (копия: `backup.sh` → `restore_check.sh`): копия 8 файлов, дамп 126 КБ, создание ≈ 1,3 с, восстановление и проверка ≈ 5,7 с; манифест OK; `versions=8 missing=0 mismatched=0 orphans=0`; `access_check documents=3 allowed_ok=3 anonymous_ok=3 errors=0` (все документы dev-БД общедоступные, поэтому `denied_ok=0` — отказ неразрешённым проверен автотестом); на копию применена 1 ожидаемая миграция; временная БД и каталог удалены. Эти цифры — на **крошечном** наборе.

**Где лежала копия в тестовых сценариях:** во временном каталоге `/tmp/talim-test-backup-*` (автотесты; удаляется после теста) и в каталоге рабочей среды (ручной прогон; удалён). На сервере — нигде: ничего не установлено.

## 9. День 14: 2FA после восстановления и план внешней копии
* **Проверка 2FA:** `restore_check.sh` вызывает `verify_restored_two_factor` (только в черновой БД, `RESTORE_CHECK=1`): расшифровывает секреты каждого подтверждённого устройства и проверяет текущий код. Вывод — только счётчики; результат `RESTORE_OK … two_factor_devices=N`. При неверном/утерянном `OTP_ENCRYPTION_KEYS` проверка падает (покрыто тестом). Проверено на одноразовых ключах; **настоящие ключи не использовались**. Ключ хранить отдельно от копий: без него пользователи не смогут войти и 2FA придётся сбрасывать вручную.
* **План внешней копии (не реализован, не проверен):** передача только завершённых копий (`ship_offsite.example.sh` — пример, **не проверен**: в песочнице нет rsync/ssh); доступ — отдельный ключ только на добавление, получатель не доверяет серверу приложения; защита от удаления — неизменяемость/снимки на стороне получателя, без `--delete`; целостность — `sha256sum --check` на получателе; проверка восстановления — еженедельно на отдельной машине, не реже раза в месяц с копией именно из внешнего хранилища; ключи (пароль копий, `OTP_ENCRYPTION_KEYS`, `talim.env`) — в отдельном месте, не рядом с копиями; при потере сервера — порядок в `DEPLOYMENT_READINESS.md` §4.14 п. 8.
* **Не проверено:** внешняя передача, восстановление на чистом сервере, RTO/RPO, ротация пароля копий.

## 10. День 15: копия как часть релиза
`deploy/staging/release.sh deploy` первым шагом вызывает команду копии (`PRE_BACKUP_CMD`); при её неудаче релиз не начинается. В песочнице это отрепетировано с настоящим `backup.sh`. Автоматического восстановления базы при неудачном релизе **нет**: миграции не откатываются, решение о восстановлении принимает оператор (`STAGING_RUNBOOK.md` §2). Восстановление на staging-сервере не выполнялось.

## 11. День 23: роли PostgreSQL для копий и восстановления
Три роли: владелец (миграции), runtime (приложение), **копии** (`deploy/postgres/create_backup_role.sql`: `CREATEDB` + `pg_read_all_data`, не суперпользователь). Право подключаться к рабочей БД роль копий получает из `apply_grants.sql -v backup_role=…`. В `backup.env` — `PGUSER=<роль копий>` (+ `PGPASSFILE`), она **не** совпадает с `DB_USER`. Проверка восстановления создаёт временную БД этой ролью и выполняет прикладные шаги тоже от неё (`DB_USER` подменяется на `PGUSER` внутри `restore_check.sh`): runtime-роль не имеет прав на временную БД и DDL. Рабочей роли `CREATEDB` не выдаётся. Отрепетировано в песочнице (`deploy/backup/verify_backup_roles.sh`, 7 проверок); `preflight.py --backup-env` проверяет роль на сервере. Защита от восстановления поверх рабочей БД: имя временной БД должно содержать `restore`/`scratch`/`check` и не совпадать с рабочей (код 2). Копии ключей (`OTP_ENCRYPTION_KEYS`, пароль копий, `talim.env`, ключ TLS) хранятся отдельно от копий данных; без `OTP_ENCRYPTION_KEYS` проверка 2FA после восстановления падает. Внешняя копия по-прежнему не реализована. **На сервере не проверялось.**

### 12.2 Безопасная процедура оператора
1. **Создание:** таймер `talim-backup_create.timer` или `sudo systemctl start talim-job@run_backup.service`. Успех = строка `BACKUP_OK name=… prune_failed=0` и статус в `job_status`. Код 4 / «retention failed» — копия создана, но диск будет заполняться: исправить права на старые копии.
2. **Проверка восстановления:** `talim-job@run_restore_check.service` (еженедельно) — восстанавливает **новейшую** копию во временную БД/каталог от роли копий, затем ставит метку `RESTORE_VERIFIED`. Не реже раза в месяц — на **другой** машине с копией из внешнего хранилища.
3. **Реальное восстановление после аварии** (автоматика его не выполняет): объявить окно потери данных (всё после времени копии теряется); сохранить текущее состояние как есть; остановить приложение; взять копию с меткой `RESTORE_VERIFIED`; расшифровать и восстановить **в чистую** БД и каталог (команды — как в шагах 3–4 `restore_check.sh`); `migrate`; `apply_grants.sql`; `verify_document_files`; `check_scanner --eicar`; вернуть `talim.env` с **теми же** `OTP_ENCRYPTION_KEYS`; владельцем восстановленного каталога документов сделать `talim`, режим 0700/0600; войти тестовым пользователем.
4. **Если копия не проходит проверку:** не удалять ничего вручную; взять предыдущую копию с `RESTORE_VERIFIED`; сообщить ответственному ([INCIDENT_RESPONSE.md](INCIDENT_RESPONSE.md)).

### 12.3 Внешнее хранение: требования (решение владельца инфраструктуры; **не реализовано, не проверено**)
Копии уже зашифрованы до выноса, поэтому отдельное шифрование на стороне хранилища желательно, но не заменяет пароль копий. Требования к месту хранения:
* **другая физическая/логическая площадка**, чем сервер приложения (потеря сервера не уничтожает копии);
* **доступ только на добавление**: у сервера приложения нет права удалять или перезаписывать (отдельный ключ или учётная запись, принудительная команда без оболочки, либо неизменяемость/object lock, либо снимки на стороне получателя); пароль копий и ключи приложения там **не** хранятся;
* **защита от случайного удаления** (версионирование/снимки, срок хранения не меньше срока ротации), раздельные учётные данные для записи и для восстановления;
* **проверка целостности после передачи** на стороне получателя (`sha256sum --check` манифеста; в примере — `ship_offsite.example.sh`), а не по коду возврата передачи; метка `RESTORE_VERIFIED` **не** отправляется (она относится к локальной копии);
* **проверка восстановления из внешней копии** на чистой машине не реже раза в месяц; запись результата, оценка RTO/RPO;
* **ключи хранятся отдельно**: пароль копий, `OTP_ENCRYPTION_KEYS`, `talim.env`, ключ TLS — не рядом с копиями данных, с описанной процедурой получения при потере сервера;
* юридическое решение о размещении (копии содержат персональные данные) — [LEGAL_AND_DATA_CHECKLIST.md](LEGAL_AND_DATA_CHECKLIST.md).
Параметры, которые должен определить оператор (названия из примера, **не** реальные значения): `OFFSITE_TARGET`, `OFFSITE_SSH_KEY` (0600), `OFFSITE_KNOWN_HOSTS` (закреплённый ключ хоста), расписание (после `backup_create`), срок хранения на стороне получателя, кто и как получает доступ при аварии. **`ship_offsite.example.sh` — пример: в песочнице нет `rsync`/`ssh`, он не запускался против реальной машины.** Фраза «внешняя копия работает» недопустима, пока передача и восстановление из неё не выполнены на реальных машинах — блокер B-22 в [STAGING_BLOCKERS.md](STAGING_BLOCKERS.md) остаётся открытым.

### 12.4 Границы
Копия защищает от потери данных, а не от того, кто знает пароль копий и имеет доступ к каталогу. Владелец БД и системный администратор с доступом к серверу могут прочитать данные приложения и ключи из окружения. Метка `RESTORE_VERIFIED` — обычный файл в каталоге копии: тот, кто может писать туда, может её поставить; она нужна для защиты от ошибок ротации, а не от злоумышленника.

### 12.5 День 26: точка подключения внешней передачи (`BACKUP_OFFSITE_COMMAND`) — провайдера нет
Единственный существовавший интерфейс — отдельный пример-скрипт без связи с задачей `run_backup`: его сбой не попадал ни в `job_status`, ни в оповещения. Добавлена **общая точка расширения, не провайдер**: в `backup.env` необязательная переменная `BACKUP_OFFSITE_COMMAND` — абсолютный путь исполняемого файла, который выберет и напишет владелец инфраструктуры. После успешного локального `backup.sh` задача `backup_create` запускает его как `<команда> <имя каталога копии>` **без оболочки**, в минимальном окружении (`PATH`, `BACKUP_DIR`, `BACKUP_NAME` и переменные `OFFSITE_*`): пароль БД, ключи OTP, секрет Django и путь к файлу пароля копий **не передаются**. Файл должен быть исполняемым и недоступным для записи группе и остальным. Ненулевой код или превышение 3 часов — задача `backup_create` **падает** с текстом «создана локально, но передача не удалась; НЕ хранится вне этого сервера» (локальная копия сохраняется), успех записывается как `offsite=ok` в заметке запуска. Подтверждено тестами `OffsiteHook` (окружение без секретов, отказ небезопасных файлов, сбой, нет оболочки; мутации ловятся) на локальной команде-заглушке. **Что это не доказывает:** ни одной настоящей передачи; провайдер, учётные данные и способ защиты от удаления остаются решением владельца. Требования к стороне хранения — §12.3; команда владельца обязана: передавать только то, что получила (каталог `talim-…` из `BACKUP_DIR`), не отправлять метку `RESTORE_VERIFIED`, проверять целостность на получателе (`sha256sum --check` манифеста), использовать отдельные учётные данные только на добавление, не хранить там пароль копий и ключи, возвращать ненулевой код при любой неполноте. **Проверка восстановления из внешней копии — отдельный обязательный шаг на чистой машине** (блокер B-22 открыт).

**День 27 — как отличить локальную копию от внешней и чего код не знает.** Код знает только код возврата команды владельца: `offsite=ok` в заметке запуска `backup_create` означает «команда вернула 0», а **не** «копия лежит и цела на другой стороне» — это проверяет команда владельца и оператор на получателе. Нет `offsite=ok` (или запуск провален) — копия только локальная. **С Дня 28 стандартный вывод и поток ошибок команды отбрасываются полностью** (иначе токен в её сообщении попал бы в журнал): в журнал и в запись запуска идёт только код возврата. Диагностику команда владельца ведёт сама (например, `logger -t talim-offsite`, без секретов). Запись запуска хранит лишь класс ошибки (`CommandError`), читаемый текст — в журнале службы. При таймауте (3 часа) завершается **вся группа процессов** команды, а не только она сама. Если одновременно упали передача и очистка, в сообщении названы обе причины. Права проверяются только у самого файла команды (абсолютный путь, исполняемый, не записываемый группой и остальными); каталог, в котором он лежит, и его конфигурацию защищает владелец (`root:talim`, `0750`/`0640`). Сбой очистки старых копий не отменяет передачу новой копии (дефект Дня 27). Таблица исходов `backup_create`: очистка ок + команда ок → успех, `offsite=ok`; очистка упала + команда ок → **провал** (диск заполняется), копия передана; команда упала или таймаут → провал, «НЕ хранится вне сервера»; оба сбоя → провал с двумя причинами; код 0 без результата → **успех** (код этого не видит — проверка на получателе обязательна). **Оператору для проверки внешней копии:** на получателе `sha256sum --check MANIFEST.sha256` в каталоге копии; затем на **чистой машине** — получить копию, пароль копий и `OTP_ENCRYPTION_KEYS` из отдельного хранилища секретов, выполнить `restore_check.sh <каталог копии>` и записать RTO/RPO. Пока это не выполнено, B-22 открыт.

### 12.6 Что доказывает успех внешней передачи (День 29)
**Код возврата 0 команды `BACKUP_OFFSITE_COMMAND` не доказывает, что копия сохранена.** Задача видит только код; `offsite=ok` означает «команда завершилась с 0». Копия считается внешней **только после трёх подтверждений**, которые выполняет оператор вместе с командой владельца и записывает вне Git: (1) **существование** — на получателе есть каталог с именем этой копии, все файлы (`MANIFEST.sha256`, `INFO.txt`, `db.dump.enc`, `files.tar.enc`), размеры совпадают; (2) **целостность** — `sha256sum --check MANIFEST.sha256` на получателе без ошибок; (3) **восстановление** — на отдельной машине из внешней копии выполнен `restore_check.sh`, итог `RESTORE_OK`. **B-22 нельзя закрыть без настоящей передачи и восстановления в отдельной среде;** ни заглушка, ни локальная имитация, ни тесты `OffsiteHook` его не закрывают (они проверяют только безопасность интерфейса).
