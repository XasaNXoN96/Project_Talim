## 2. Сравнение

Оценка по пятибалльной шкале (5 — лучше). Баллы — экспертное суждение, а не измерение; обоснование приведено в таблице.

| Критерий | Django (+ PostgreSQL) | Next.js fullstack (+ PostgreSQL) | Комментарий |
|---|---|---|---|
| **Сложность самостоятельной разработки с Claude** | **5** | 3 | В Django готовы пользователи, права, формы, админка, миграции, сессии: почти всё CRUD «настраивается», а не пишется. В Next.js нужно выбрать и связать библиотеки авторизации, ORM, валидации, загрузки файлов, а админку — писать целиком. Каждая такая связка — дополнительная точка отказа и ошибка безопасности |
| **Сохранение текущего HTML/CSS/JS** | **5** | 2 | HTML-страницы становятся шаблонами Django почти без переделки (общий каркас → базовый шаблон). В Next.js страницы переписываются в React-компоненты: это перенос всего интерфейса |
| **Авторизация и разграничение прав** | **5** | 3 | Django: хэширование паролей, сессии, защита от CSRF, группы и права — из коробки и десятилетиями проверены. Next.js: используются сторонние библиотеки; популярные решения в этой области менялись и выходили из поддержки, их надо отслеживать. Права на уровне записей в обоих стеках придётся писать, но в Django для этого есть устоявшиеся приёмы |
| **Документы, файлы, отчёты** | 4 | 3 | Django: загрузка файлов, проверка, раздача с проверкой прав, выгрузки в CSV/XLSX делаются средствами фреймворка и небольших библиотек. Next.js: возможно, но каждую часть собираем сами |
| **Стоимость сервера и поддержки** | 4 | 3 | Django — один процесс, скромные требования, обычный VPS. Next.js с серверным рендерингом — Node-процесс, по памяти обычно прожорливее; поддержка двух экосистем (npm и сборка React) чаще ломается при обновлениях |
| **Безопасность и тестирование** | **5** | 3 | Django: включённые по умолчанию защиты (CSRF, экранирование шаблонов, защита от SQL-инъекций ORM), встроенный тестовый клиент, поддержка проверок безопасности (`check --deploy`). В Next.js безопасность во многом зависит от выбранных библиотек и дисциплины разработчика |
| **Дальнейшее расширение** | 4 | 5 | Next.js лучше для сложных интерактивных интерфейсов и мобильных клиентов. Для Django при появлении мобильного приложения добавляется API (Django REST Framework) — это известный путь, но потребует работы |
| **Итого (простая сумма)** | **32 / 35** | 22 / 35 | Разрыв большой, но он отражает именно **ваши** условия (один разработчик, минимум бюджета, готовый HTML) |

### Честные оговорки
- Если вы **уже хорошо знаете JavaScript/TypeScript и не знаете Python**, разрыв сократится: сложность разработки с Claude тогда оценивается ближе к равной. Но на сохранении HTML и готовой админке Django всё равно выигрывает.
- Баллы по Next.js предполагают «полностековое» использование без отдельного API. Прежний вариант Next.js + NestJS в таблицу не включён: он сложнее обоих.
- Оценки не проверены на этом проекте. Они будут проверены на этапах 1–3 (см. «Условия пересмотра»).

## 3. Решение

> **Основной стек: Django + PostgreSQL**, серверные шаблоны, постепенный перенос текущих HTML-страниц.
> Веб-сервер: Nginx перед Gunicorn. Сессии, очереди и кэш — на PostgreSQL. Дополнительных сервисов на старте нет.

### Версии (проверить при старте этапа 1)
По официальной странице загрузки Django (через поиск, 2026): **Django 5.2 LTS** поддерживается до **апреля 2028**; **6.2 LTS** запланирован на **апрель 2027** с поддержкой до апреля 2030; версия 6.0 не LTS (поддержка до апреля 2027).
Рекомендация: **начать на 5.2 LTS** и **запланировать переход на 6.2 LTS** после его выхода и обкатки (отдельный небольшой этап в плане, ориентировочно 20–40 часов). **[Версии, сроки и поддерживаемые версии Python подтвердить на djangoproject.com перед этапом 1.]**

## 4. Что не добавляем сейчас и когда добавим

| Компонент | Сейчас | Условие, при котором добавляем | Более дешёвая замена до этого |
|---|---|---|---|
| Отдельный API (NestJS / DRF) | Нет | Мобильное приложение или внешние клиенты | Серверные шаблоны |
| Redis | Нет | Чат на WebSocket с несколькими процессами или заметная нагрузка на очередь/кэш | Сессии и кэш в БД |
| WebSocket / ASGI | Нет | Пилот показал, что обновление раз в 3–5 секунд для чата недостаточно | Короткий опрос (polling) для уведомлений и чата |
| Очередь задач (Celery и т. п.) | Нет | Отправка писем и обработка файлов заметно тормозит запросы | Команды по расписанию (cron) и обработка при загрузке |
| Отдельный поиск (Elasticsearch и т. п.) | Нет | Полнотекстовый поиск PostgreSQL перестанет хватать | Поиск в PostgreSQL |
| S3-хранилище | Нет | Диск сервера заполнен или нужна резервная копия на уровне объектов | Файлы на диске, копирование наружу |
| CDN | Нет | Страницы медленные за пределами города | Кэш Nginx |
| Фронтенд-фреймворк (React/Vue) | Нет | Появятся экраны, где серверных шаблонов явно недостаточно | Небольшой JS как сейчас |
| HTMX / Alpine | Не обязательно | Захочется убрать полную перезагрузку на фильтрах и вкладках | Обычные формы и ссылки |

Чат — единственная функция макета, которая может потребовать WebSocket. Начинаем с короткого опроса. Для 50–100 сотрудников этого, как правило, достаточно, но **это нужно проверить в пилоте**.

## 6. Структура проекта (предложение, не создаётся на этапе 0)

Эталон макета **остаётся в текущем репозитории `Project_Talim`** (замороженный, с тегом `design-v1`, демо на GitHub Pages не затрагивается); приложение создаётся **в новом репозитории** — решения P-02, P-03 в [STAGE_0_PLAN.md](STAGE_0_PLAN.md).


```
config/            # настройки (dev / staging / production)
apps/
  core/            # общее: базовые модели, сервис загрузки файлов, права
  accounts/        # пользователи, вход, 2FA, роли
  organization/    # подразделения, должности, учреждения, сотрудники
  content/         # новости, педагоги, медиа, документы публичные
  documents/       # внутренние документы
  tasks/           # задания
  notifications/   # уведомления
  attendance/      # приход-уход, геозоны
  chat/            # чат
  reports/         # отчёты
  audit/           # журнал аудита
templates/         # базовые шаблоны: public_base.html, portal_base.html
static/            # CSS, JS, шрифт, иконки из design-v1
tests/
docs/
design-v1/         # эталон: текущие HTML-страницы для сверки
```

### Как переносится текущий макет
| Сейчас | В Django |
|---|---|
| `styles.css` | `static/css/` без изменений |
| Шапка, подвал, сайдбар, топбар (собираются JS) | Базовые шаблоны `public_base.html` и `portal_base.html` |
| Иконки (JS-строки) | SVG-спрайт, подключаемый шаблоном (работает без JS) |
| `app.js` (сайдбар, окна, вкладки, лайтбокс) | Остаётся как улучшение страниц |
| `pages.js`, `data.js` | Уходят: данные и фильтры — на сервере |
| Тексты интерфейса | Помечаются для перевода (gettext) с первого шаблона; перевод — позже |
| Имитация входа, 13 видов «Maket»-действий (19 кнопок) | Реальные функции по таблице в [FEATURE_ROADMAP.md](FEATURE_ROADMAP.md) |

Встроенную админку Django используем **как внутренний инструмент технического администратора** (справочники, срочные правки), а **не как интерфейс сотрудников**: для сотрудников остаются страницы портала в дизайне макета. Доступ к `/admin/` ограничивается отдельно (роль, 2FA, при необходимости — адрес).

## 7. Риски выбора и как их снижаем

| Риск | Снижение |
|---|---|
| Вы раньше не работали с Python/Django | Первые два этапа (фундамент, безопасность) играют роль обучения; на них же калибруются оценки; ChatGPT как независимый проверяющий |
| Полные перезагрузки страниц на фильтрах выглядят «тяжело» | Допустимо на этом объёме; при желании добавить HTMX точечно |
| Пользовательский интерфейс сложнее, чем шаблоны выдерживают (чат) | Пилот чата на опросе; при необходимости добавить ASGI/WebSocket отдельным этапом |
| Версии Django устаревают | План обновления до 6.2 LTS; регулярные обновления безопасности |
| Админка Django визуально другая | Не показывается сотрудникам |
| Сложность прав на уровне записей | Единая функция проверки прав + автотесты «роль × ресурс × действие» с первого модуля |

## 8. Условия пересмотра решения

Пересмотреть выбор, если:
1. После этапа 2 фактические трудозатраты **более чем вдвое** превысили оценку и причина в стеке, а не в объёме.
2. Появилась обязательная потребность в мобильном приложении или сложном «живом» интерфейсе (тогда добавляется API, а не меняется стек).
3. Заказчик или хостинг предъявил требование, которое Django не удовлетворяет.

До этого момента вопрос стека закрыт.
