# Требования к безопасному production-развёртыванию

**Статус:** черновик, День 2. Это список того, что должно быть выполнено и **проверено** до первого запуска для реальных пользователей. Ничего из перечисленного ниже не настроено «по умолчанию на сервере»: сервера пока нет.
Пункты со знаком ⛔ — **блокирующие**: без них запускать нельзя. Юридические вопросы — в [LEGAL_AND_DATA_CHECKLIST.md](LEGAL_AND_DATA_CHECKLIST.md).

## 3. Настройки окружения для production

Обязательные переменные: `DJANGO_SETTINGS_MODULE=config.settings.production`, `DJANGO_SECRET_KEY` (≥ 50 случайных символов), `DJANGO_ALLOWED_HOSTS`, `DJANGO_ADMIN_URL` (нестандартный путь), `DB_*`, `OTP_ENCRYPTION_KEYS`, `EMAIL_HOST` (+ `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`), `DEFAULT_FROM_EMAIL`, `DJANGO_CSRF_TRUSTED_ORIGINS`, за прокси — `DJANGO_TRUSTED_PROXIES` (адреса или сети самого прокси, через запятую; **не** сеть пользователей). Переменная `DJANGO_BEHIND_TLS_PROXY` больше не используется: схема HTTPS определяется только для доверенных прокси.
Приложение **откажется стартовать**, если не заданы ключ, хосты, ключ OTP, SMTP или адрес отправителя (проверено тестами).
Cookie в production называются `__Host-sessionid` и `__Host-csrftoken` (только HTTPS, без домена): локально, по HTTP, они не работают — это ожидаемо.

## 4. Сервер и сеть

- Приложение запускается под непривилегированным пользователем за Nginx; наружу — только 80/443; PostgreSQL доступен только с локального адреса или частной сети.
- Роль БД приложения **без** прав суперпользователя и создания баз; для таблицы журнала аудита — запрет `UPDATE`/`DELETE` на уровне БД (сейчас защита только в приложении).
- Ограничение размера тела запроса и частоты на уровне Nginx (дополнительно к приложению); отдельное, более строгое ограничение для `/accounts/` и `/csp-report/`.
- Автоматические обновления безопасности ОС; регулярное обновление зависимостей и автоматическая проверка уязвимостей (`pip-audit` или аналог).
- Закрытый доступ к админке Django: нестандартный путь + ограничение по адресам (если возможно) + обязательная 2FA (уже требуется).

## 5. Двухфакторная аутентификация: процедуры

**Первоначальная настройка (никто не блокируется).** Новый или существующий администратор вводит логин и пароль → система сразу открывает страницу настройки → QR/ключ → ввод кода → показ 10 резервных кодов (один раз) → вход. Хранить коды — в менеджере паролей или в запечатанном конверте. Протестировано.
**Потерян телефон.** Войти резервным кодом (каждый работает один раз), затем «Безопасность → Обновить резервные коды». Оставшихся мало — система предупреждает.
**Потеряны телефон и все коды.** Только через сервер: `python manage.py reset_2fa <логин>`. Перед этим **личность человека подтверждается вне системы** (лично или по заранее согласованному каналу), решение фиксируется письменно. Команда закрывает все сессии пользователя, пишет событие в аудит; при следующем входе пользователь настраивает 2FA заново. Протестировано.
**Потерян ключ `OTP_ENCRYPTION_KEYS`.** Секреты расшифровать нельзя: нужен `reset_2fa` для всех. Поэтому ключ хранится отдельно и копируется надёжно (B-7). Для ротации: добавить новый ключ **первым** в список, оставив старый; после перешифровки старый можно убрать (перешифровка пока не автоматизирована).
**Доверенных сессий («не спрашивать 30 дней») нет** — второй фактор требуется при каждом новом входе.

## 6. CSP: порядок перехода к блокирующему режиму

1. Сейчас: `Content-Security-Policy-Report-Only` + приём отчётов на `/csp-report/` (с ограничением размера и частоты, без query-строк в журнале).
2. Неделя наблюдения на staging/production: смотреть журнал `CSP report:`; прогнать все страницы, включая админку Django (**пока в браузере не проверялась**).
3. Устранить причины нарушений; убрать `style="…"` из шаблонов и дизайн-системы и **удалить** исключение `style-src-attr 'unsafe-inline'`.
4. Включить блокирующий режим: `DJANGO_CSP_REPORT_ONLY=0`; оставить приём отчётов.
5. Любое новое внешнее подключение (карта, шрифты, аналитика) — только осознанным решением и с юридической проверкой (L-30).

## 7. Известные ограничения (остаются после Дня 2)

| Ограничение | Влияние | План |
|---|---|---|

| Нет уведомления о входе с нового устройства (уведомления о смене пароля, включении/отключении 2FA и сбросе 2FA — есть, День 3) | Меньше шансов заметить захват учётной записи | Добавить |
| Django-админка (`/admin/`, только суперпользователи) обходит уровни доступа к полям сотрудников и **не пишет в журнал чтение** личных данных | Суперпользователь видит всё без записи в журнал | Не выдавать суперпользователя без необходимости; закрыть `/admin/` по адресу на прокси |
| Сброс 2FA — только командой на сервере | Нужен доступ к серверу | Допустимо для малого числа администраторов |
| Пароль: минимум 12 символов, проверка на частые и числовые; без проверки по утёкшим базам | Слабые, но «нормальные» пароли возможны | Рассмотреть проверку по базе утечек |
| Журнал аудита защищён только на уровне приложения | Администратор БД может изменить записи | Ограничить права роли БД (раздел 4) |
| Не проверено: нагрузочное поведение, работа за реальным прокси, реальный SMTP | — | До запуска (B-1, B-5) |
| Админка Django под **включённой** CSP проверена в настоящем браузере (суперпользователь с 2FA: главная, пользователи, сотрудники, форма добавления, журнал, группы): нарушений 0, оформление загружается. Политика ради админки не ослаблялась | — | Повторить при обновлении Django |


## 8. Пример конфигурации Nginx для B-1 (НЕ ПРОВЕРЕНО на реальном сервере)

```nginx
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;   # перезаписываем, а не дописываем: клиентскую цепочку отбрасываем
    proxy_set_header X-Forwarded-Proto $scheme;
}
```
В окружении Django: `DJANGO_TRUSTED_PROXIES=127.0.0.1,::1` (если Nginx и Gunicorn на одной машине). Gunicorn должен слушать только `127.0.0.1` или unix-сокет, иначе клиент сможет обратиться к нему напрямую.


## 9. Документы и уведомления (День 4)

**Что защищает загрузку:** лимит размера; белый список расширений; расширение, заявленный MIME и содержимое должны согласоваться (сигнатура PDF/PNG/JPEG, структура ZIP для DOCX/XLSX/PPTX/ODT/ODS, UTF-8 для TXT); запрет двойных расширений (`x.php.pdf`); отказ для SVG/HTML/XML/архивов/файлов с макросами, PDF со скриптами или вложениями, подозрительных ZIP (обход пути, «бомба», шифрование); случайное имя на диске, права 0600; имя клиента хранится только для показа; файл отдаётся только после проверки прав, как вложение с нейтральным типом.

**Чего это НЕ даёт.**
- **Антивирус (День 5):** загрузки сканируются ClamAV до сохранения, **fail-closed** (сканер недоступен/тайм-аут/ошибка → файл отклонён); production не запускается с `DOCUMENT_SCAN_MODE=disabled`. См. [CLAMAV.md](CLAMAV.md). ⚠️ Проверено с настоящим `clamd`, но **на локально созданной сигнатуре EICAR**: официальную базу в среде скачать не удалось, поэтому ловит ли официальная база на вашем сервере — не проверено. Антивирус не даёт гарантии отсутствия вредоносного содержимого.
- Проверка активного содержимого PDF — эвристика по ключевым словам; она может отвергнуть редкий безобидный файл и не гарантирует отсутствие эксплойтов.
- Загрузка целиком читается в память (лимит 10 МБ) — для больших файлов нужен другой механизм.

**Эксплуатация.**
| Пункт | Требование |
|---|---|
| Каталог файлов | `DJANGO_PRIVATE_MEDIA_ROOT` — вне каталога сайта и статики, на постоянном диске, права только для пользователя приложения, **входит в резервное копирование вместе с БД** (иначе версии документов станут «битыми» ссылками) |
| Размер запроса | Nginx: `client_max_body_size 11m` в шаблоне; загрузка 10 МБ проверена через настоящий Nginx в тестовой среде (на боевом сервере — нет) |
| Nginx | Не раздавать `private_media`/`/media` напрямую; отдача только через приложение |
| Планировщик | `python manage.py send_task_reminders` — раз в час. Файлы таймера/cron готовы (`backend/deploy/systemd/`), команда идемпотентна и параллельно-безопасна, **но на сервере таймер не установлен** → напоминания сами не создаются. См. [SCHEDULER.md](SCHEDULER.md) |
| Права ролей | После каждого `migrate` — `python manage.py seed_roles` |
| E-mail копии уведомлений | Выключены (`NOTIFICATION_EMAILS_ENABLED=0`); включать только после настройки и проверки SMTP (B-5); письмо содержит тип события и название задания, без ссылок |
| Админка | Документы и файлы в Django-админке **не зарегистрированы** намеренно (иначе обход уровней доступа и журнала скачиваний). Доступна только категория документов |
| Журнал | Загрузка, новая версия, просмотр конфиденциальных, скачивание, правка (имена полей), архив, восстановление, отклонённая загрузка (только код причины); содержимое и имена файлов в журнал не пишутся |

**Известные ограничения:** уведомления хранятся без срока очистки; нет публичных документов; нет «удаления» версий (только архив документа).


## 10. Вложения заданий (День 5)
Используют тот же путь, что и документы (проверка типа → антивирус → приватное хранилище → скачивание только как вложение): отдельного обходного кода нет. Права: прикреплять — исполнитель или руководитель задания, только пока задание открыто; скачивать — все, кто видит задание (в том числе у закрытых/отменённых, **без расширения** круга доступа); отвязать — загрузивший или руководитель, только у открытого задания. Отвязка не удаляет файл с диска (след для аудита и копий). Подмена идентификаторов: вложение другого задания → 404, чужое задание → 403. Всё пишется в аудит (id вложения, расширение, размер; без имён и содержимого) и в историю задания.

### Примечание к Дню 9 (новости и просмотр документов)
Добавлены портал управления новостями и просмотр документов в портале; ни один пункт таблицы выше они **не закрывают**. Что нового с точки зрения риска:
* Просмотр отдаёт PDF и изображения с `Content-Disposition: inline`, фиксированным типом, `nosniff`, `X-Frame-Options: SAMEORIGIN` и CSP `default-src 'none'` — только после проверки доступа. CSP страниц портала **не ослаблялась** (`frame-ancestors 'none'` и `default-src 'self'` остались; фрейм того же источника разрешён общим `default-src`). PDF и изображения из загрузок проходят ту же проверку содержимого и антивирус, что и скачивание; без реального ClamAV (см. выше) оговорка остаётся.
* Не проверено: поведение встроенного просмотрщика PDF в Firefox/Safari/мобильных браузерах; влияние на нагрузку при большом числе одновременных просмотров; хранение просмотров конфиденциальных документов в аудите (срок хранения — юридический вопрос).
* Новости: простой текст без форматирования, поэтому санитайзера HTML нет и не требуется; при добавлении форматированного текста санитайзер обязателен. Право публикации у контент-менеджера — решение заказчика (схема «автор → редактор» не включена).

### Примечание к Дню 10 (импорт сотрудников и поиск)

### Примечание к локализации (День 7)
Cookie языка в production называется `__Host-django_language` и ставится только по HTTPS (`Secure`, `Path=/`): как и остальные `__Host-` cookie, работает только на HTTPS-хосте без `Domain`. Переключатель языка — POST с CSRF; адрес возврата проверяется на внешние перенаправления. Локализация не меняет ни права, ни проверки доступа (проверено тестами для трёх языков). Строки в `.po` не содержат секретов и данных пользователей. Риски из таблицы выше (B-1, B-7, ClamAV, планировщик, SMTP, аудит, юридические вопросы) локализацией **не затронуты и остаются открытыми**.
