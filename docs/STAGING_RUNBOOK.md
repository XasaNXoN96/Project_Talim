# Staging: порядок запуска оператором (День 15)

**Статус.** Staging-сервер, домен, сертификат, SMTP и официальная база ClamAV в этой работе **не были доступны**. Staging **не запускался**. Ниже — процедура и автоматические проверки, которые оператор выполняет сам; для каждого шага указано, что из него уже отрепетировано в песочнице (скрипты `backend/deploy/staging/verify_*.sh`) и что можно проверить только на настоящем сервере. Данные — только вымышленные. Никаких адресов, доменов и секретов в репозитории нет: везде `<…>` и `CHANGE_ME`.

Подробный порядок сборки сервера — `DEPLOYMENT_READINESS.md` §4; здесь — то, что добавилось для staging.

## 0. Что нужно от владельца инфраструктуры (до начала)
Отдельный сервер/ВМ (не production); имя хоста и DNS-запись; сертификат от доверенного центра (например, ACME) — получает и устанавливает владелец; почтовый шлюз для тестовых писем; доступ к серверам сигнатур ClamAV; письменное подтверждение, что на сервере будут только вымышленные данные. **Файрвол, DNS и сертификаты оператор сам не меняет без подтверждения владельца.**

Команды (значения подставляет оператор; пароли не вводить в командной строке, использовать файлы с правами 0600):
```
# предпроверка (от talim)
/srv/talim/backend/.venv/bin/python /srv/talim/backend/deploy/staging/preflight.py --env-file /etc/talim/talim.env --backend /srv/talim/backend --backup-env /etc/talim/backup.env
# релиз (от talim); значения — из окружения оператора
export RELEASES_DIR=/srv/talim/releases CURRENT_LINK=/srv/talim/backend HEALTH_URL=http://127.0.0.1:8000/healthz/
export HEALTH_HOST=<хост из DJANGO_ALLOWED_HOSTS>     # нужен: проверка идёт на 127.0.0.1 с заголовком X-Forwarded-Proto: https (иначе production-настройки отвечают 301)
export RESTART_CMD='sudo systemctl restart talim-gunicorn'            # sudoers: только эта команда (пример, не проверялся)
export PRE_BACKUP_CMD='set -a; . /etc/talim/talim.env; . /etc/talim/backup.env; set +a; /srv/talim/backend/deploy/backup/backup.sh'
export MIGRATE_CMD_PREFIX='env DB_USER=<роль-владелец> DB_PASSWORD=<вводится оператором на время релиза, не сохраняется>'   # миграции — ролью владельца
export POST_MIGRATE_SQL_CMD='psql -h 127.0.0.1 -U <роль-владелец> -d <БД> -v app=<роль-приложения> -v db=<БД> -v backup_role=<роль-копий> -f /srv/talim/releases/<тег>/backend/deploy/postgres/apply_grants.sql'   # пароль владельца — через PGPASSFILE (файл 0600), не в команде
/srv/talim/backend/deploy/staging/release.sh deploy <тег>
# снаружи, с другой машины
python3 smoke_remote.py https://<хост> --admin-path <путь>
```
Примечание: как безопасно передать пароль владельца (переменная только на время сеанса, файл с правами 0600) оператор выбирает на месте — это **не** отрепетировано (в песочнице миграции идут ролью приложения).

## 2. Откат и восстановление
* Автоматически (`release.sh deploy`): состояние сохраняется (резервная копия, шаг 1 — при её неудаче релиз **не начинается**); `migrate`; `collectstatic`; переключение ссылки; перезапуск; опрос `/healthz/` до 60 с. При неуспехе ссылка возвращается и служба перезапускается: код `1` (вернулся прежний релиз) или `3` (прежний тоже не отвечает — срочное вмешательство).
* Вручную: `release.sh rollback`; `release.sh status`.
* **Миграции не откатываются автоматически.** Если новый релиз применил миграции и не стартовал, прежний код продолжает работать с новой схемой; если он ведёт себя неверно — решение о восстановлении БД и документов из копии шага 1 принимает оператор (`BACKUP_AND_RESTORE.md`, затем `restore_check.sh` как образец; восстановление «боевой» базы автоматикой не выполняется).
* Что отрепетировано (`deploy/staging/verify_release.sh`, песочница, настоящие gunicorn/PostgreSQL/`backup.sh`, пользователь без привилегий): первый релиз; обычное обновление; релиз с миграцией, который не стартует → возврат и честное предупреждение; релиз с падающей миграцией → прежний продолжает работать; отказ копии → ничего не меняется; ручной откат; отказ запуска от root; негативный контроль (без проверки здоровья сломанный релиз остаётся). Репетиция нашла и исправила ошибку: после автоматического возврата запись «предыдущий релиз» указывала на текущий.
* **Не проверено:** откат на настоящем сервере под systemd, права `sudoers`, восстановление базы после неудачной миграции на реальных объёмах, вход пользователя после отката (проверка входа и сценариев — ручной пункт §4.16).

## 4. Что нужно получить до реального запуска (проверено в День 16: ничего из этого в текущей среде нет)
**Ресурсы:** отдельный сервер/ВМ (≥ 2 vCPU, 4 ГБ ОЗУ, 40 ГБ), имя хоста с DNS-записью, доверенный сертификат (ACME или от владельца), почтовый шлюз с тестовым ящиком, доступ ВМ к серверам сигнатур ClamAV, второй каталог или машина для проверки восстановления.
**Разрешения (письменно от владельца инфраструктуры):** на развёртывание именно на этом сервере; на открытие портов 80/443; на выпуск сертификата; на правило `sudoers` для `systemctl restart talim-gunicorn`; подтверждение, что данные только вымышленные.
**Передать оператору:** доступ к репозиторию (чтение), этот документ, `DEPLOYMENT_READINESS.md` §4 и §6. Секреты оператор создаёт на сервере сам; в чат, Git и журналы они не попадают.

## 5. Проверки, которые невозможно выполнить без сервера (на День 16 не выполнены)
Реальная цепочка TLS и `smoke_remote.py` без `--insecure-self-signed`; вход, 2FA, сброс пароля с реальным письмом, роли, новости, документы, импорт Excel, поиск и сессии в браузере по HTTPS; отправка через SMTP; ClamAV с официальной базой; запуск служб и таймеров под systemd; релиз и откат под systemd; резервная копия и восстановление на втором окружении; журналы staging на отсутствие секретов; ротация журналов.
В песочнице эти пункты **воспроизводимо** покрыты только на уровне логики (см. §1–3); это не заменяет проверку на сервере.
