Статика 0600 (nginx не прочёл бы); проверка восстановления от неверной роли; падение 2FA-входа при нечитаемом ключе (HTTP 500) и страницы настройки; `/healthz/` не замечал забытые права БД; пропуск внешней передачи при сбое очистки старых копий; stderr внешней команды в журнале; не завершались дочерние процессы по таймауту; потеря причины при двойном сбое; утечка временных каталогов тестов. **Открытых подтверждённых дефектов кода нет.**

## 4. Блокеры запуска (все открыты)
* **B-06** — ClamAV на сервере: официальные сигнатуры, служба `clamd`, `check_scanner --eicar`, EICAR отклонён, fail-closed при остановленном `clamd` (процедура C-1…C-8 в `CLAMAV.md`).

## 7. Что нельзя выполнить без инфраструктуры
Без **сервера** — шаги 2, 6, 7, 9; без **домена и TLS** — шаг 3 (доверенная цепочка, браузер); без **SMTP** — шаг 4 (настоящая доставка); без **настроенного ClamAV** с официальной базой как служба — шаг 5; без **внешнего хранилища** и второй машины — шаги 7–8. Пока их нет, B-06 и B-22 остаются открытыми, а никакие песочничные результаты их не закрывают.

## 9. Разделение задач
**А. Можно выполнить сейчас, без сервера**
* Отправить владельцу `OWNER_HANDOFF.md`, `PROJECT_STATUS_AND_STAGING_PLAN.md` §8 и получить сроки/ответственных (письменно).
* Оператору прочитать `STAGING_OPERATOR_CHECKLIST.md` целиком и выписать вопросы; выбрать имя релиза `<тег>` (например, дата + короткий хеш `d8c02cc`).
* Заранее подготовить на отдельной (не staging) машине черновики окружения **без значений**: `talim.env`, `backup.env` по `deploy/staging/talim.env.staging.example`; список имён секретов и мест их хранения (менеджер секретов владельца).
* Убедиться, что клон кандидата воспроизводим: `release_info.sh` на чистом checkout `d8c02cc` даёт хеши из `OWNER_HANDOFF.md` §1; `pip install --require-hashes -r requirements.txt` в чистом venv.
* Слепой прогон чек-листа человеком вне проекта (бумажный, без сервера): записать непонятные места.

**Б. Сразу после выдачи доступа (в таком порядке)**
1. Проверить, что это не production и нет реальных данных; получить письменное разрешение (§3 чек-листа).
2. Чек-лист шаги 1–2: пакеты, пользователь `talim`, каталоги.
3. Шаг 4: PostgreSQL с тремя ролями.
4. Шаги 5–6: окружение на сервере (секреты создаёт оператор на месте), checkout `d8c02cc`, `release_info.sh`, миграции, `apply_grants.sql`, `seed_roles`, `preflight.py` (+ `--backup-env`) → `PREFLIGHT OK`.
5. gunicorn, ClamAV (`CLAMAV.md` C-1…C-3), nginx — после того как владелец установит сертификат.
6. `smoke_remote.py https://<хост>` без обхода проверки сертификата.
7. SMTP-тест, systemd-таймеры, `run_backup` / `run_restore_check`.

**В. Требует отдельного подтверждения владельца**
* Правило `sudoers` только для `systemctl restart talim-gunicorn`; открытие портов 80/443; выпуск сертификата и запись DNS.
* Выбор внешнего хранилища, автор и сопровождение команды передачи; хранитель и места копий ключей (`OTP_ENCRYPTION_KEYS`, пароль копий, `talim.env`, ключ TLS).
* Мониторинг, канал оповещений, дежурный и порядок эскалации (`INCIDENT_RESPONSE.md` утвердить).
* Запуск тестов ClamAV C-4 с временной ролью `CREATEDB` (политика БД владельца).
* Решение о допуске к пилоту, любое принятие риска по блокерам, решения заказчика B-25 и юридические ответы.

## 10. Первый шаг после получения сервера
Получить письменное разрешение и убедиться, что сервер отдельный и без реальных данных; затем на сервере выполнить `git clone` репозитория, `git checkout d8c02ccd785cc0fcde89348f0cc69bb21eaa40a0` и `backend/deploy/staging/release_info.sh` — сверить хеши с `OWNER_HANDOFF.md` §1. Расхождение — остановиться. Дальше — чек-лист §5 с шага 1.
