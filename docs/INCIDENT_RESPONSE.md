# Реагирование на инциденты — ЧЕРНОВИК (День 14)

**Статус:** черновик, **не утверждён**. Не проверен учениями. Ответственные лица, каналы связи и сроки уведомления — решения заказчика (см. `DEPLOYMENT_READINESS.md` §9, вопрос L-07 в `LEGAL_AND_DATA_CHECKLIST.md`). В документе нет адресов, телефонов и значений секретов; их нужно вписать в закрытом хранилище заказчика, а не в Git.

## 1. Роли (назначает заказчик)

| Роль | Задача | Кто |

## 2. Первые 30 минут (общие шаги)

1. Зафиксировать время и источник сигнала. Ничего не удалять и не «чистить» до копирования следов.
2. Оценить масштаб: какие учётные записи, документы, период.
3. Остановить рост ущерба: заблокировать затронутые учётные записи (`is_active=False`), при необходимости остановить `talim-gunicorn`; сессии завершить (`clear_expired_sessions` не заменяет принудительный выход — удалить сессии пользователя вручную).
4. Сохранить журналы: `AuditLog` (только добавление), журналы приложения и nginx (без query-строк и токенов сброса), `JobRun`.
5. Записать решения в журнал инцидента (вне Git).

## 3. Сценарии

**Взлом учётной записи.** Блокировка → сброс пароля и 2FA (устройство удалить, пользователь заново подключает) → просмотр `AuditLog` по этому пользователю за период → оценка доступных ему документов (по роли и объектным правам) → уведомление владельцев данных при необходимости.

**Подозрение на утечку документов.** Выявить документы по аудиту скачиваний; `verify_document_files` для проверки целостности; решение об уведомлении принимает юрист (L-07).

**Компрометация ключей** (`DJANGO_SECRET_KEY`, `OTP_ENCRYPTION_KEYS`, пароль БД, пароль копий). Считать сервер скомпрометированным; сменить значения вне Git; для OTP — добавить новый ключ первым и выполнить `rotate_otp_keys`, затем убрать старый после проверки; `DJANGO_SECRET_KEY` — все сессии станут недействительны (ожидаемо). Пароль копий: новые копии с новым паролем, старые хранить, пока нужны, с известным старым паролем.

**Потеря основного сервера.** Порядок — `DEPLOYMENT_READINESS.md` §4.14 п. 8 и `BACKUP_AND_RESTORE.md`. Восстановление на чистом сервере **ещё не отрабатывалось** (риск).

**Вредоносный файл.** Документ остаётся в карантине (ClamAV); проверить `check_scanner`; повторное сканирование; уведомить автора.

**Отказ почты/ClamAV/БД.** См. страницу «Фоновые задачи» в портале (`JobRun`) и `SCHEDULER.md`.

Разбор причин, правка кода с регрессионным тестом, обновление `DEPLOYMENT_READINESS.md`, проверка, что журналы не содержат лишних данных.
