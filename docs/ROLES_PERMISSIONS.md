# Роли и права доступа

Предложение для согласования. Роли соответствуют разделам, уже нарисованным в интерфейсе (сайдбар портала, кнопки «Xodim qo‘shish», «Topshiriq yaratish», «Yangi yangilik» и др.).

## 1. Роли

| Роль | Кто | Основные возможности |
|---|---|---|
| **Гость** | Любой посетитель | Публичный сайт: новости, педагоги, медиа, структура, открытые документы |
| **Сотрудник** | Работник отдела | Портал: свои задания, документы своего уровня, уведомления, чат, отметка прихода, свой профиль |
| **Руководитель подразделения** | Начальник отдела | Всё как у сотрудника + создание заданий и контроль в своём подразделении, отчёты подразделения, согласование |
| **Контент-менеджер** | Пресс-служба, методист | Создание и правка новостей, фото, видео, профилей педагогов; публикация — по настройке (сразу или после согласования) |
| **Кадровик (HR)** | Отдел кадров | Управление сотрудниками, подразделениями, сертификатами, отчёты по посещаемости, доступ к контактным данным |
| **Администратор** | Руководство / IT | Всё по организации: пользователи, роли, справочники, настройки, отчёты, журнал аудита |
| **Системный администратор** | IT-специалист | Техническое: резервные копии, настройки безопасности, интеграции. Не обязан видеть персональные данные сотрудников |

Принцип: **минимум необходимых прав**. Роли суммируются (например, сотрудник + контент-менеджер).

## 2. Область действия (scope)

| Значение | Смысл |
|---|---|
| `own` | Только собственные записи |
| `department` | Записи своего подразделения |
| `all` | Вся организация |

## 4. Правила

1. **Проверка на сервере.** Скрытие кнопок в интерфейсе — удобство, а не защита. Каждый запрос API проверяет право и область.
2. **Защита от подмены идентификатора (IDOR).** Запрос чужого `id` без права возвращает «не найдено».
3. **Персональные данные:** выдача только при праве, чтение карточки пишется в аудит.
4. **Публикация:** материал виден гостям только в статусе `published` и, где нужно, с подтверждённым согласием на изображения.
5. **Администраторы:** обязательная 2FA, отдельные учётные записи (не общая «admin»), срок жизни сессии короче.
6. **Отзыв доступа:** блокировка пользователя немедленно завершает его сессии.
7. **Тесты:** автоматическая проверка «каждая роль × каждый ресурс × действие» — обязательная часть CI.

## День 21: Django admin и безопасный `seed_roles`

### Что можно делать в Django admin (только суперпользователям; остальным — 403/вход)
| Объект | Политика | Журнал (AuditLog) |
|---|---|---|
| **Новость** | правка текста (заголовок, ссылка, краткое описание, текст, категория) — разрешена; **статус, дата публикации, автор — только чтение**; новость «на проверке» **заморожена**; правка текста **одобренной** возвращает её в черновик с записью в истории; создание и удаление запрещены (в т. ч. массовое) | `admin_changed` (имена полей, `approval_reset`) |
| **История согласования (`NewsReview`)** | в админке **не зарегистрирована**: ни просмотра, ни правки, ни удаления | — |
| **Пользователь** | правка имени, e-mail, языка, флагов активности/staff/superuser и **личных разрешений** — разрешена; создание, удаление, установка пароля — **запрещены** (портал: приглашение, принудительная смена пароля, деактивация); группы (роли) — только чтение | `admin_changed` (имена полей, флаги «было → стало», добавленные/снятые разрешения по коду); попытка задать пароль — `admin_blocked` |
| **Группа** | шесть+ ролевых групп из кода (`RoleCode`): имя и права **только чтение**, удалять нельзя; прочие группы — правка и удаление разрешены | `admin_changed` (добавленные/снятые разрешения), `admin_deleted` |
| **Назначение роли** | только просмотр; назначать и снимать — в портале (там права выдачи привилегированных ролей, область, «последний администратор») | — |
| **Сотрудник** | правка разрешена; удаление запрещено (архив в портале) | `admin_changed` (только имена полей; личные данные не записываются) |
| **Подразделение, должность, учреждение, категории новостей и документов** | правка и удаление разрешены | `admin_created/changed/deleted`; массовое удаление — по записи на объект (`bulk`) |
| **Документы, версии, файлы, уведомления, сессии, 2FA** | в админке нет | — |
| **Журнал аудита** | только чтение, удаление и массовые действия недоступны | — |
В журнал **не** попадают значения полей: ни пароли и хеши, ни тексты новостей, ни внутренние заметки, ни персональные данные — только имена полей, коды разрешений и три безвредных флага. Журнал пишется в транзакции самой админки (откат изменения — откат записи). Собственный журнал Django admin (`LogEntry`) продолжает вестись как прежде.

### Граница модели угроз
Аудит фиксирует действия, выполненные через приложение (портал и админку) под учётной записью. Он **не защищает** от владельца базы данных и системного администратора с доступом к серверу или БД: они могут менять данные и (с правами владельца) даже журнал. Рабочая роль приложения не может изменять журнал (`deploy/postgres`), копии шифруются, но это граница, а не гарантия. Суперпользователь по-прежнему может выдать себе любое разрешение через админку (это журналируется, но не предотвращается); доступ к админке — по закрытому адресу, с 2FA, и только у минимума людей.

### `seed_roles`: как запускать безопасно
```bash
python manage.py seed_roles --dry-run     # план по ролям: + добавит, = нестандартное (останется), ничего не меняет
python manage.py seed_roles               # добавляет недостающие права и создаёт отсутствующие группы
python manage.py seed_roles --dry-run --prune   # что удалилось бы
python manage.py seed_roles --prune       # ТОЛЬКО осознанно: удаляет права, которых нет в определении роли
```
* Обычный запуск **не удаляет** ничего: права, добавленные к ролевой группе вручную, остаются, но **каждый раз выводятся в stderr** (`= perm kept`). Удаляет только `--prune` (с выводом `- perm … REMOVED`).
* Не трогает пользователей, назначения, личные разрешения, членство в группах и группы, не относящиеся к ролям; не выдаёт права суперпользователя. Повторный запуск с теми же данными ничего не меняет (проверено).
* Исключения («одобрить своё») выдавайте **персонально** (личное разрешение пользователя в админке — это журналируется), а не добавлением в группу роли.
* Если команда показала неожиданное нестандартное право: выяснить по журналу аудита (`admin_changed`, `Group`/`User`, `permissions_added`), кто и когда его добавил; при необходимости `--dry-run --prune`, затем `--prune`; зафиксировать в журнале инцидентов.


## Этап А: школы как участники системы
- **Роль `school_director` («Muassasa direktori»)**, область `institution`: видит список сотрудников и контакты **только своей школы** (школа берётся из его карточки сотрудника), работает с назначенными ему заданиями, видит документы своего уровня и уведомления. **Этап Б:** ведёт состав своей школы — добавляет, правит и архивирует карточки сотрудников школы без аккаунта (ФИО, должность, рабочий телефон и e-mail, статус, фото). Поля «отдел», «школа», «аккаунт» и личные данные (дата рождения, личный телефон, дата приёма) ему не показываются и не принимаются; школа и отдел подставляются сервером. Не видит структуру отдела, другие школы, не пользуется импортом из Excel и админ-хабом, не управляет пользователями.
- **Из школы входит только директор.** Остальные сотрудники школы — записи (карточки без аккаунта). Один активный директор на школу.
- Аккаунт директора создаётся одним действием («Foydalanuvchilar → Yangi»: роль + школа): создаются пользователь, карточка сотрудника (отдел «Ta’lim muassasalari», должность «Maktab direktori») и назначение роли; пароль директор задаёт по приглашению.
- **Фото сотрудника:** JPG/PNG до 5 МБ → общая проверка + антивирус → перекодируется в JPEG 512×512 (метаданные удаляются) → приватное хранилище, случайное имя, без публичного адреса. Отдаётся только тем, кто видит этого человека в списке сотрудников (тот же запрос); старый файл при замене/удалении стирается.
- Должности: `python manage.py seed_positions` (стартовый список, правится в портале).

## Этап В: задания школам
- Задание можно дать **учреждению**: в форме задания поле «Ta’lim muassasalari» (только тем, у кого право создавать задания на всю организацию). Задание получает директор выбранного учреждения; если у учреждения нет аккаунта директора, форма называет его и ничего не создаёт. Школу видно рядом с ответственным в списке и в карточке задания.
- Срочность: Past / Oddiy / Yuqori / **Shoshilinch** (новая, выделена красным).
- Срок: дата + **время** (необязательное; без времени срок до конца дня). Просрочка считается с этой минуты; отчёты («просрочено», «выполнено с опозданием») учитывают время. Напоминания (`send_task_reminders`) по-прежнему считаются по дате.
- Директор школы видит только задания, назначенные ему; задания других школ — 403.
