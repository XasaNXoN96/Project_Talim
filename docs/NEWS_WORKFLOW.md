# Согласование и публикация новостей (День 18)

Реализация: `backend/apps/content/workflow.py` (одно место, где решается, какой переход допустим и для кого), `manage_views.py`, модель `NewsReview` (история), уведомления `Notification.news`, аудит. Публичный сайт показывает только `published` с наступившей датой (`News.objects.published()`), как и раньше.

## Статусы и переходы
```
черновик ──отправить──▶ на проверке ──одобрить──▶ одобрено ──опубликовать──▶ опубликовано ──снять──▶ черновик
   ▲                       │   └─вернуть (комментарий обязателен)─▶ требуются исправления
   └────отозвать───────────┘                                              │
   └────────────────────────── отправить снова ◀──────────────────────────┘
архив: из любого, кроме архива (право публикации) → «вернуть из архива» → черновик
```
| Действие (`/portal/news/<id>/<действие>/`) | Из статусов | В статус | Нужно право | Дополнительно |
|---|---|---|---|---|
| `submit` отправить на проверку | draft, changes_requested | review | `change_news` | автор записи или тот, у кого `review_news`/`publish_news` |
| `withdraw` отозвать | review | draft | `change_news` | как выше |
| `request_changes` вернуть | review | changes_requested | `review_news` | комментарий обязателен (≤ 2000); **не свою** новость |
| `approve` одобрить | review | approved | `review_news` | комментарий по желанию; **не свою** новость |
| `publish` опубликовать | **approved** | published | `publish_news` | будущая дата = расписание, остаётся |
| `unpublish` снять | published | draft | `publish_news` | требует нового согласования |
| `archive` в архив | draft, review, changes_requested, approved, published | archived | `publish_news` | |
| `restore` из архива | archived | draft | `publish_news` | |

**Изменение действующей схемы (сознательное):** раньше публиковать можно было прямо из черновика/«на проверке». Теперь публикация возможна **только из «одобрено»**; иначе обойти согласование мог бы любой, у кого есть право публикации. Остальные функции (создание, поиск, фильтры, расписание, архив, возврат) работают как прежде.

## Права
* Новое право `content.review_news` — «проверять»: роли `content_manager` и `admin` (как и `publish_news`). Право `content.approve_own_news` — исключение «одобрить свою новость»: **не входит ни в одну роль**; выдаётся отдельно и осознанно. Права суперпользователя **не** считаются: исключение должно быть выдано явно (`workflow.holds_explicitly`), и в истории виден исполнитель.
* Правка: автор правит свои черновики, «требуются исправления» и «одобрено» (с правом `change_news`); чужие — только с `review_news` или `publish_news`. Новость «на проверке» **заморожена** (проверяющий видит ровно тот текст, что отправлен): сначала «отозвать». Опубликованное и архивное правит только `publish_news`. **Правка одобренной новости возвращает её в черновик** (запись в истории «изменено после одобрения»); сохранение без изменений одобрение не снимает.
* Всё проверяется на сервере при каждом запросе (`PortalPermissionMixin` + `workflow.check_actor`), кнопки лишь отражают правила. GET никогда не меняет состояние; CSRF обязателен.
* Неавторизованные и посторонние пользователи не видят ни портал новостей, ни статусы; публично видны только опубликованные.
* **Для штатной работы нужны минимум два человека** с `review_news` (автор и проверяющий), либо отдельная роль «автор» без `review_news`. По умолчанию один `content_manager` не сможет одобрить собственную новость. Заказчику нужно решить: нужны ли отдельные роли «автор»/«редактор» (сейчас права можно выдавать по отдельности, готовой роли нет) и допускать ли `approve_own_news` для малых команд.

## История, аудит, уведомления
* `NewsReview`: автор действия, время, переход (из/в), комментарий — для каждого шага; записи только добавляются, правки нет. Видна в предпросмотре тем, у кого `view_news`. Последний комментарий проверяющего показан автору над текстом.
* Аудит (`AuditLog`): `news_submitted`, `news_withdrawn`, `news_changes_requested`, `news_approved`, `news_published`, `news_unpublished`, `news_archived`, `news_restored`; в `meta` — переход и **длина** комментария, не сам текст.
* Уведомления (раздел «Уведомления»): проверяющим — «на проверке» (кроме автора и самого действующего, неактивным не шлются; повторная отправка не создаёт дублей); автору — «возвращена на доработку» и «одобрена». В уведомление не копируется комментарий. Раздел уведомлений открывается по праву `tasks.view_task`, у `content_manager`/`admin` оно есть; у «чистого» проверяющего без него раздела нет (ограничение).

## Конкуренция и повтор
* Решение выполняется в транзакции с блокировкой строки новости: из двух одновременных решений проходит одно, второй получает «Bu amalni hozirgi holatda bajarib bo‘lmaydi» (проверено потоками на отдельных соединениях).
* Решение несёт «версию» текста (`updated_at`), которую проверяющий видел; если текст изменился (отозвали → правка → отправили снова), старое решение отклоняется. Запрос без версии тоже отклоняется.
* Повторная отправка формы не создаёт второй записи истории, уведомления или аудита.

## Что проверено
Автотесты `apps/content/tests_workflow.py` (38 тестов): полный цикл с историей/аудитом/уведомлениями; матрица «статус × действие»; обходы прав прямыми POST (анонимный, сотрудник, автор без права проверки, проверяющий без права публикации, публикатор без права проверки, свои новости, суперпользователь); CSRF; устаревшая и отсутствующая версия; гонка двух потоков; правка после одобрения, в проверке, чужая, опубликованная; расписание; невидимость для публики и поиска; кнопки по ролям; перевод статусов UZ/RU/EN. Браузер (Playwright, блокирующая CSP, 1440 и 390 px, UZ/RU/EN): без нарушений CSP, без горизонтальной прокрутки страницы, без непереведённых строк. Прежние тесты модуля обновлены только там, где менялась схема (прямая публикация из черновика заменена прохождением согласования).

## Ограничения и риски

Комментарий хранится открытым текстом и виден всем с `view_news`. ## День 19: готовые роли, права уведомлений, приватные заметки

### Готовые роли (`seed_roles`; переиспользуют существующие права)
| Роль (Group) | Права | Что делает | Чего не может |
|---|---|---|---|
| `news_author` — Автор | `view_news`, `add_news`, `change_news` | пишет и правит **свои** материалы, отправляет на проверку, видит решения и комментарии по своим новостям | одобрять, возвращать, публиковать |
| `news_editor` — Редактор | `view_news`, `review_news` | видит присланное на проверку, одобряет или возвращает (комментарий обязателен), может оставить внутреннюю заметку | писать, публиковать; одобрять своё |
| `news_publisher` — Публикатор | `view_news`, `publish_news` | публикует **только одобренное**, снимает с публикации, архивирует/возвращает в пределах видимого | одобрять, писать, публиковать черновик |
Всем трём также выдано `notifications.view_notification`. `content_manager` и `admin` **не менялись** (кроме того же права уведомлений); ни одна роль не содержит `approve_own_news`. Существующие назначения и роли не удаляются и не меняются; `seed_roles` лишь создаёт недостающие группы и выставляет им права (идемпотентно). Новые роли видны в форме «Назначить роль» с пояснениями (UZ/RU/EN); привилегированные роли по-прежнему выдаёт только администратор. **После обновления кода выполнить `manage.py migrate` и `manage.py seed_roles`.**

### Видимость материалов в портале
Автор видит только свои; редактор — присланные на проверку и дальше (чужие черновики — нет); публикатор — одобренные, опубликованные, архивные; роли, которые и пишут, и проверяют/публикуют (content_manager, admin, суперпользователь), видят всё. Чужой материал — **404**, а не 403 (`workflow.visible_news`; применяется к списку, просмотру, правке, шагам и уведомлениям). Прежнее поведение «любой с `view_news` видит всё» сохраняется только для ролей из последней группы. Если выданы нестандартные наборы прав (например, только `view_news`), такой человек видит лишь свои материалы.

### Уведомления больше не зависят от задач
Раздел «Уведомления» требует `notifications.view_notification` (стандартное право модели, новых механизмов нет), а не `tasks.view_task`. Колокольчик в шапке — по тому же праву. Чтобы **никто не потерял доступ при обновлении**, миграция `notifications.0003` выдаёт это право всем группам и пользователям, у которых было `tasks.view_task` (только добавляет; откат — намеренно пустой). Чужие уведомления по-прежнему недоступны (404 на прочтение/открытие чужого идентификатора, «прочитать всё» — только свои); уведомление о новости ведёт к материалу только пока человек его видит, иначе — сообщение и возврат к списку; заголовок такого материала в списке не показывается. `sysadmin` уведомлений не имел и не имеет.

### Комментарии: автору и внутренние заметки
* **Комментарий автору** (`NewsReview.comment`) — виден всем, кто видит материал, включая автора; при возврате обязателен.
* **Внутренняя заметка** (`NewsReview.internal_note`, новое поле, необязательна, ≤ 2000) — только сотрудникам редакции (`review_news`/`publish_news`) и **не автору этого материала** (даже если он по роли редактор), не обладателям одного `view_news`. Хранится только для решений (одобрить/вернуть); для остальных шагов игнорируется. Перед выводом в шаблон блокируется на сервере (`history_for`), не только скрывается.
* В уведомления и в журнал аудита тексты не попадают: аудит хранит только **длины** (`comment_length`, `note_length`), в журналы приложения не пишется ничего; вывод экранируется.
* **Миграция `content.0003`** добавляет `internal_note` со значением «пусто». Все прежние записи истории сохраняют текст в `comment`, где он всегда был виден автору, — ничего автоматически не переклассифицируется и не скрывается задним числом (проверено тестом на настоящей миграции вперёд с данными прежней схемы).

### Остаются рисками
Переводы новых строк — автором кода, не носителями. Нет напоминаний о долго висящих проверках и отдельного экрана «моя очередь». Редактор не может писать, а автор — видеть чужие решения: для малых команд по-прежнему удобнее `content_manager` + второй проверяющий. Миграции и `seed_roles` на реальном сервере не выполнялись. Внутренние заметки хранятся открытым текстом в БД (как и прочие данные приложения; доступ — права БД и копии шифруются).
